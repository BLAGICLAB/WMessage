# `From<String>` 降级的复发防护：三个待拍板的选项

> 2026-10-26 · 起因：实机故障 trace_id=11 的根因链里，「流内错误被降级成不可恢复的
> `INTERNAL`」是三处放大器之一（另两处：流内错误不重发、用户没有重试入口）。
> 那次只修了流内错误这一个降级点，顺手查清了 blanket 降级的全量旧账——本文件是
> 那笔旧账的处置方案，**待拍板**，本轮未实施。

## 一、事实（实测，非估计）

### 陷阱本体

`src-tauri/src/error.rs`：

```rust
impl From<String> for CommandError {   // → Internal
impl From<&str>  for CommandError {   // → Internal
```

两者都把任意字符串压成 `Internal`。`Internal` 在 `is_recoverable()` 里恒为
`false` → 前端 hint 是「不可自动重试；请反馈日志（含复现步骤）」。

**问题不在 `Internal` 本身**——真内部故障（线程 join 失败、HTTP client 构建失败、
base64 解码失败）用 `INTERNAL` 是对的。问题在于**降级是隐式的**：写
`Err(format!("…"))` 或 `?` 一个 `Result<_, String>`，就自动变成了「不可恢复的
内部错误」，作者不写错也踩。

### 规模

- 2026-10-26 那次实机故障是它第一次造成用户可见后果（前端没有「重试」入口）。

## 二、三个选项

### 选项 A：编译器逼出显式选型（删掉两个 blanket impl）

**做法**：删 `From<String>` / `From<&str>`，262 处编译错误逐点改成显式变体。
- 真内部故障 → `CommandError::Internal(…)`（行为零变化，机械替换）。
- 语义性失败 → 各自的精确变体（`TaskInvalidState` / `InvalidArgument` /
  `TaskNotFound` / `LlmApiError` …）。

**代价**：262 处，~35 个文件；**会改一批内部函数签名**——`Err(String)` 的内部函数
必须改成返回 `CommandError` 或在边界 `map_err`，否则 `?` 编译不过。这正是历史
上「逐点改函数签名绕开」那条老路，2026-10-09 走过一次。

**收益**：**根除**。编译器保证，之后不可能再写出新的隐式降级——不需要任何人的
自觉，也不需要门禁脚本去猜文本形态。

**风险**：一次性大改。每个 commit 要小步（建议按模块分 5–6 批），且**语义性失败的
变体选择会改 `recoverable` 与前端 hint**，必须逐点确认，不能批量替换。

### 选项 B：保留 impl + 加「新增行」门禁 + 逐点精确化语义失败

**做法**（三件配套）：
1. **新增行门禁**：仿 `scripts/test-fast.sh` 里已有的「工单号防线」——扫描本次改动
   的新增行，命中 `CommandError::from(` / `.into()` 到 `CommandError` 的降级就 fail，
   行内加 `audit-ok` 可放行。**存量 78 处不动**（它们是历史事实，不是新增）。
2. **逐点精确化语义失败**：把剩下 7 处语义性失败改成精确变体。
3. **在 `error.rs` 的 impl 上写明「这是陷阱」**：注释点明它会把字符串压成
   `Internal`、新代码应显式选变体。

**代价**：门禁脚本约 1 个文件（~80 行）+ 7 处逐点改。

**收益**：新增的降级进不来；语义性失败（真正影响用户体验的那 7 处）被清掉；
**零运行时风险**（不动存量行为）。

**缺点**：中间态仍可被 `audit-ok` 行内豁免绕过——是「提醒」不是「封锁」。且门禁
只拦新增，存量里那 69 处真内部故障仍写着 `INTERNAL`（它们本来就对，但形态上
看不出是「有意选 Internal」还是「顺手降级」）。

### 选项 C：只加「新增行」门禁（最小改动）

**做法**：只做选项 B 的第 1 件。

**代价**：最小。

**收益**：防住新增，零运行时风险。

**缺点**：剩下的 7 处语义性失败仍会被误判成不可恢复错误——**用户可见的后果还在**。

## 三、对比

| | A：删 impl | B：门禁 + 精确化 7 处 | C：只门禁 |
|---|---|---|---|
| 封死复发机制 | **彻底** | 防新增（可豁免） | 防新增（可豁免） |
| 清掉用户可见后果 | 是 | **是** | 否（剩 7 处） |
| 改动量 | 262 处 / ~35 文件 | ~7 处 + 1 脚本 | 1 脚本 |
| 改函数签名 | **是**（老路） | 否 | 否 |
| 运行时风险 | 中（逐点确认变体） | 低 | 无 |

## 四、建议

**推荐 B**：它的收益覆盖了用户真正在意的两件事（新增的降级进不来 + 现存的用户
可见后果清掉），成本低、不碰函数签名、不改运行时行为。

**不推荐 A 的理由**：262 处里 253 处是「真内部故障 → 继续 `INTERNAL`」，为这 253 处
去改 35 个文件的函数签名，收益只是「形态好看」——`INTERNAL` 对它们本来就是对的。
真要「彻底」，更划算的做法是**只删 `From<String>` 保留 `From<&str>`**、或反过来先
删 `From<&str>`（`Err("字面量".into())` 这种写法少），把爆炸半径压到能一批评完的
规模，再考虑剩下的。

**不推荐 C 的理由**：它留着 7 处用户可见后果——这次实机故障就是被这 7 处里的
某一种咬到的（`recoverable=false` → 前端不给重试入口）。只堵新增而不清存量，
等于「下次同一个坑换个文件再踩一次」。
