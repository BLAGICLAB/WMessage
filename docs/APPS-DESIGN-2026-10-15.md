# 程序设计：开发模块（聊天即 IDE）+ 程序页（运行态）

> 2026-10-15 立项。前身「工作流画布」（任务卡 DAG + LLM 逐节点执行）已退役，
> 退役理由与数据留档口径见 `DEVLOG.md` 2026-10-15 段。M1 拍板改名 toolbox → apps；
> 目录落在 `{data_dir}/apps/<id>/`（用户数据同级）；程序页是「运行态」+「上架
> 入口」，开发态仍走挂件聊天窗口，不在程序页里同屏。

## 1. 一句话

程序里的每个「程序」= 大模型**开发时**写好的一个确定性小程序（脚本 + 输入声明），
用户**运行时**点一下就跑：不连大模型、不花 token、离线可用、同输入必同输出。

| | 旧画布工作流（已退役） | 程序 |
|---|---|---|
| 本质 | LLM 按卡图干活 | LLM 写好的程序干活 |
| 运行时依赖 | 必须连大模型 | 完全离线 |
| 适合 | 一次性的模糊目标 | 每月重复的固定流程、即时查询 |
| 速度/成本/确定性 | 慢 / 费 token / 有随机性 | 秒级 / 零成本 / 可复核 |

## 2. 工具的对象模型

```
工具 = 元数据 + 输入声明 + 脚本本体 + 说明书
```

- **元数据**：名称、图标、一句话说明（列表页展示）
- **输入声明**（二选一，存 JSON）：
  - 文件夹模式：无表单，约定目录输入输出；
  - 表单模式：字段数组 `[{key, label, type: text|number|date, required, placeholder}]`
    （前端据此渲染弹窗）
- **脚本本体**：一段 Python 源码（复用 py/ 执行器与文档族先例：openpyxl 等）
- **说明书**：大模型生成脚本时一并产出的人话说明——这个程序做什么、要放什么
  文件、点哪里、出什么（小白看得懂的「全貌」）

### 文件夹约定（每个工具一个目录）

```
apps/<app_id>/
├── data/      # 常驻数据（如姓名-身份证对照表；人员变动才更新）
├── input/     # 每次运行前放入的输入（如本月原始工资单）
├── output/    # 运行产物（脚本写入；时间戳子目录防覆盖）
└── runs.jsonl # 运行历史（本地追加）
```

「把数据放进工具的文件夹、点一下出结果」是用户直觉，目录即契约。

## 3. 运行态（程序页）

- 左导航新增「程序」视图：程序卡列表（图标/名称/说明 + 运行按钮）
- **文件夹模式**：点运行 → 脚本带 `data/ input/ output/` 路径启动 → 完成通知 +
  结果面板（open output 目录 + 摘要）
- **表单模式**：点运行 → 按输入声明渲染弹窗 → 参数以 JSON 文件传给脚本 →
  结果面板展示脚本返回的结构化 JSON（键值/小表）
- 运行历史：时间、状态、耗时、摘要一行一条；失败展示 stderr 摘要
- 执行器复用 `py/` 子进程框架（超时/内存/CPU 限额、独立临时目录、kill_tree），
  **零 LLM 参与**

### 脚本契约（开发时大模型必须遵守，运行器校验）

- 开头**校验段**：检查 input 文件存在、期望列名齐全——格式对不上要响亮报错
  （中文报错写进 stderr），宁可失败不可猜测。这是对「输入格式漂移」的防线
- 结束前打印一行结果 JSON（`##RESULT## {...}` 哨兵）供结果面板展示；
  产物文件写 output/
- 匹配类工具的规则：唯一键优先（如身份证号，不用姓名）、匹配不上的行输出
  「未匹配清单」不许静默跳过、中文 CSV 注意 GBK/UTF-8

## 4. 开发态（聊天即 IDE）

**不建专门开发界面**。开发 = 在聊天里说「帮我做一个工资单匹配工具」：

1. 大模型用读文件工具看用户给的真实样例 → 用 ask_user 问清含糊处
   （「补贴有两列以哪个为准？」——看着数据问，比表单/画布问得准）
2. 生成脚本 + 输入声明 + 说明书，落库为一个工具（草稿态）
3. 用户**试跑**（真实数据抽验，财务类必须）→ 满意后上架（草稿 → 启用）
4. 修改也在聊天里：「这个月模板加了一列，改一下」→ 大模型改自己写的脚本

需要的 bot 工具（进 TOOLS_TABLE）：`apps_create`（落库草稿）、
`apps_update`（改脚本/声明/说明）、`apps_list`（列已有程序防重名）。
试用运行复用运行态执行器。

**为什么不保留旧画布当开发界面**：画布节点是自然语言目标，到确定性脚本之间
隔着一次 LLM「编译」，改节点 ≠ 改程序，小白无法复核编译产物；而让大模型改
它自己写的脚本，因果链最短。开发是低频事件且有 LLM 牵着走，界面为「规格问清」
优化即可——聊天 + 真实文件就是最优解。

## 5. 数据模型

- 新表 `apps`（id/name/description/icon/input_schema/script_path/
  manual/status: draft|enabled|enabled_at/created_at/updated_at）
  ——不复用遗留 `workflows` 表（名字与语义都已让位）
- 脚本文件落 `{data_dir}/apps/<id>/app.py`，库里只存路径（与技能系统同思路）
- 运行历史 `app_runs`（id/app_id/started_at/finished_ms/status/summary），
  保留最近 N 条（对齐 trace 保留期口径）

## 6. V1 范围 / 明确不做

**做**：对象模型 + 执行器接线、程序页（列表/表单弹窗/结果/历史）、三个 bot
工具、文件夹约定、脚本契约校验、通知中心运行完成消息。

**不做（YAGNI，出现第二个真实需求再议）**：定时自动跑（到点可挂 schedule_jobs
机制）、可视化/表单式开发向导、工具分享导出导入、脚本联网权限细分（默认信任
本机单用户）、非 Python 脚本语言。

## 7. 风险与对策

| 风险 | 对策 |
|---|---|
| 输入格式漂移脚本就断 | 脚本契约强制校验段 + 响亮中文报错；改版回聊天让 LLM 改 |
| 脚本正确性（财务数据） | 上架前必须真实数据试跑；匹配规则写进脚本契约 |
| Windows 绿色版 Python 依赖 | py_env_check 已有；打包清单与 Word/Excel 工具族同源验收 |
| 身份证号等敏感数据 | 全程本地；脚本默认不联网；运行历史/日志不落敏感明文 |
| 工具越攒越多 | V1 只做列表不分类；超过一屏再议搜索/分组 |

## 8. 里程碑

1. **M1 运行态（仅架子）**：apps 表 + 执行器接线 + 程序页（不造真实小程序，
   工资单匹配、名册查询）——先有「点一下就跑」的体验
2. **M2 开发态**：三个 bot 工具 + 脚本契约提示词（开发走聊天）
3. **M3 打磨**：运行历史、完成通知、图标、空态/引导

M1 完成即可真机验收（拿真实工资单跑通），M2 之后再谈替代手工造工具。
