### ACC-I-01 · 多会话聊天

- **SPEC**：3-33
- **层级**：L1+L2（自动档 `src/components/ChatPanel.send.test.tsx`；实机档见下）
- **历史卡**：S19,S20（部分）
- **前置**：机器人总开关已开；已配至少一个可用模型；数据目录里已有若干历史会话
- **步骤**：
  1. 左导航「Agent 能力 → 聊天」进聊天页，点会话栏顶「新建对话」，输入「第一句」回车，等回复出完。
  2. 再点一次「新建对话」，输入「第二句」回车；随后在左栏点回第一条会话，再点回第二条。
  3. 在输入框键入 `/` 看补全列表；依次执行 `/clean`、`/compact`、`/retry`、`/stop`。
  4. 悬停左栏任一会话条目 → 点右下角删除键 → 系统弹窗点「取消」；再悬停另一条 → 删除 → 点「确定」。
- **判据**：
  1. 【可观测】左栏出现两条独立条目；发过首轮的那条标题自动改成用户消息前 20 字，没发过的那条仍是「新对话」；点哪条，聊天头部标题与消息区内容都切到哪条。
  2. 【可观测】键入 `/` 浮出的补全列表恰为四条：`/stop` 停止当前回复、`/compact` 压缩对话上下文、`/clean` 清空当前对话、`/retry` 重新生成上一条回复；列表中没有 `/help`。
  3. 【可观测】`/clean` 后消息区清空并露出空会话引导卡，左栏该条目仍在；`/compact` 后消息区只剩一条以「📦 上下文已压缩（原 N 条消息）：」开头的助手消息；`/retry` 后从最后一条用户消息重新出答复；无在途回复时 `/stop` 给出一行「当前对话没有进行中的回复」。
  4. 【可观测】删除确认是系统原生警告弹窗，正文为「删除对话「<标题>」？消息记录一并删除。」；点「取消」条目保留，点「确定」条目从左栏消失。
  5. 【可审计】`"~/Library/Application Support/com.renshi.wmessage/bot.log"` 中本轮出现 `llm.request` 与 `llm.response`；本轮调用过工具时另有 `tool.call` 与 `tool.return`。
  6. 【可核对】`sqlite3 "~/Library/Application Support/com.renshi.wmessage/wmessage.db" "select session_id, role, substr(content,1,12) from bot_messages order by created_at"` 中两条会话的用户行分别落在各自 session_id 下，互不串台。
- **证据**：截图（左栏两条条目 + `/` 补全列表 + 删除确认弹窗）+ `"~/Library/Application Support/com.renshi.wmessage/bot.log"` 片段（检索命令：`grep -F "llm.request" "~/Library/Application Support/com.renshi.wmessage/bot.log" | tail -20`）
- **失败处置**：先分清「应用坏了」还是「卡片过期」——用 `grep -F "llm.request" src-tauri/src` 确认事件名还在源码里；斜杠命令清单以 `src/components/ChatPanel/constants.ts` 的 SLASH_COMMANDS 为准，条目数或文案对不上就是卡片过期。
- **缺口补验**：斜杠命令 /compact /retry /clean、删除确认 60s 超时自动拒未验 —— 补验点：①消息少于 2 条时 `/compact` 只给「消息太少，暂无需压缩」不压缩；②无用户消息时 `/retry` 只给「没有可重试的消息」；③「60s 超时自动拒」**不属本卡**：会话删除走系统原生对话框（`src/lib/useConfirm.ts`），没有 60s 倒计时，60s 自动拒是 ACC-I-12 ConfirmMap 的口径，在该卡验。

### ACC-I-02 · 本地提示是纯瞬态

- **SPEC**：3-34
- **层级**：L1+L2（自动档 `src/components/ChatPanel.send.test.tsx`；实机档见下）
- **历史卡**：S20（部分）
- **前置**：机器人总开关已开；已配至少一个可用模型
- **步骤**：
  1. 在一个空会话里输入 `/stop` 回车 —— 消息区出现一行本地提示「当前对话没有进行中的回复」。
  2. 重载聊天页（⌘R），回到同一会话。
  3. 回到同一会话发一句「刚才那条提示写的是什么？」，让模型复述它看到的上下文。
  4. 另开一个会话，在回复进行中再发一条消息 —— 出现本地提示「⏳ 本对话正在回复中：可切换到其他对话发送，或输入 /stop 停止本条」。
- **判据**：
  1. 【可观测】提示行出现在消息区，它不是模型答复形态：没有活体指示、没有工具折叠行、没有「正在思考」字样。
  2. 【可观测】重载后回到同一会话，消息区**不再显示**该提示行（空会话则回到引导卡）。
  3. 【可核对】`sqlite3 "~/Library/Application Support/com.renshi.wmessage/wmessage.db" "select count(*) from bot_messages where content like '%没有进行中的回复%'"` 返回 0 —— 提示没进历史库。
  4. 【可核对】第 3 步模型答复里**不含**「当前对话没有进行中的回复」这句提示原文 —— 提示没进模型上下文。
  5. 【可审计】`"~/Library/Application Support/com.renshi.wmessage/bot.log"` 中第 3 步只有 1 条 `llm.request` —— 提示不是一条对话内容，不会引发额外请求。
- **证据**：截图（提示行 + 重载后的同一会话）+ `"~/Library/Application Support/com.renshi.wmessage/bot.log"` 片段（检索命令：`grep -F "llm.request" "~/Library/Application Support/com.renshi.wmessage/bot.log" | tail -20`）+ sqlite 查询输出
- **失败处置**：先分清「应用坏了」还是「卡片过期」——用 `grep -F "llm.request" src-tauri/src` 确认事件名还在源码里；提示是否落库看 `src-tauri/src/db/bot_history.rs` 的整段覆盖写与前端 `src/components/ChatPanel/useChatSend.ts` 的 `!m.hint` 过滤。
- **缺口补验**：只覆盖停止回显；/compact 不足 /retry 不可重试等提示不落库未验 —— 补验点：在「消息少于 2 条」的会话触发 `/compact`、在「没有用户消息」的会话触发 `/retry`，各自重复第 2–4 步（重载后提示消失 + 库查询 0 行 + 模型复述里没有提示原文）。

### ACC-I-03 · 停止有回显：停了多少条

- **SPEC**：3-35
- **层级**：L1+L2（自动档（无）；实机档见下）
- **历史卡**：S20（全）
- **前置**：机器人总开关已开；已配至少一个可用模型；当前会话有一条正在跑的回复
- **步骤**：
  1. 在聊天页发一句会跑较久的请求（例如「用 run_python 打印 1 到 100 并 sleep 20 秒」），等流式开始。
  2. 点输入卡内的红描边圆形停止键（title 为「停止当前回复」）。
  3. 另开一个会话，在**没有**在途回复时点同一个停止键。
  4. 在第 2 步的会话里再发一条新消息，观察停止反馈行是否还在。
- **判据**：
  1. 【可观测】停止后输入区**上方**出现一行「⏹ 已停 N 条」，N ≥ 1（鼠标悬停提示为「本会话被置停止标志的执行条数」）。
  2. 【可观测】该行不在消息流里：它不是消息区里的助手气泡，位置在输入卡正上方。
  3. 【可观测】被停的这一轮已流出的正文**保留**在原助手气泡里，不被清空或替换。
  4. 【可观测】无在途回复时点停止：不出现「已停 0 条」，改为消息区一行本地提示「当前对话没有进行中的回复」。
  5. 【可观测】开始下一轮消息后，第 1 步那行「⏹ 已停 N 条」消失（它说的是上一轮的事）。
  6. 【可审计】`"~/Library/Application Support/com.renshi.wmessage/bot.log"` 出现一行 `bot_stop | session: <会话 id>`（检索命令：`grep -F "bot_stop" "~/Library/Application Support/com.renshi.wmessage/bot.log" | tail -20`）。
- **证据**：截图（输入区上方的停止反馈行 + 保留正文的助手气泡）+ `"~/Library/Application Support/com.renshi.wmessage/bot.log"` 片段（检索命令：`grep -F "bot_stop" "~/Library/Application Support/com.renshi.wmessage/bot.log" | tail -20`）
- **失败处置**：先分清「应用坏了」还是「卡片过期」——用 `grep -F "bot_stop" src-tauri/src` 确认停止留痕与置位计数还在源码里（`src-tauri/src/bot_slash.rs`）；反馈行位置看 `src/components/ChatPanel/ChatPanel.tsx` 的 stopNotice 渲染块。
- **缺口补验**：—（本行历史覆盖度为「全」，本次只补实机留证；补验点：停止计数 N 与 `bot_stop` 返回值一致——同会话并行两条执行时 N = 2，界面上不得显示 1）。

  5. 【可观测】聊天头部看不到任何活体指示（头部只有标题与三个图标钮）。

- **缺口补验**：气泡内四段次序（活体→思考→工具→子 agent→正文）未验 —— 补验点：必须一轮里同时凑齐四段（配了带思考模式的模型 + 一个会调工具的请求 + 一次派子 agent）；凑不齐时逐段单独验，缺哪段记哪段未验。

- **层级**：L2（自动档 `src-tauri/tests/task_chat_exec.rs`；实机档见下）
- **历史卡**：—（无）
- **前置**：机器人总开关已开；已配至少一个可用模型；有一张可执行的任务卡
- **步骤**：
  1. 记下当前会话列表（会话数与各条标题）。
  2. 在任务卡上点 🤖 执行按钮，等执行结束。
  3. 看会话列表新增了什么；点进那条新会话。
  4. 建一条定时任务（每天），把时间设到 1 分钟后，等它自动跑完。
  5. 看会话列表新增了什么。
- **判据**：
  1. 【可观测】任务卡 🤖 执行后，会话列表**新增一条会话**，标题以「📋 任务：」开头（后接任务标题前 30 字）；执行不发生在当前会话里。
  2. 【可观测】点进新会话，第一条消息是应用拼装的任务块（带任务 id 与标题），随后是本轮执行的结果。
  3. 【可观测】定时任务到点执行后，会话列表**又新增一条会话**，标题以「⏰ 定时：」开头（不是复用已有会话）。
  4. 【可核对】`sqlite3 "~/Library/Application Support/com.renshi.wmessage/wmessage.db" "select id, title, is_exec from bot_sessions order by created_at desc limit 5"` 中两条新会话的 `title` 前缀分别为「📋 任务：」与「⏰ 定时：」，`is_exec` 为 1。
  5. 【可核对】一次执行只对应**一条**新会话（第 2 步与第 4 步各自只 +1 条，不多不少）。
  6. 【可审计】`"~/Library/Application Support/com.renshi.wmessage/bot.log"` 中本轮执行有 `llm.request` 与 `llm.usage` 记录，事件归属新会话。
- **证据**：截图（执行后的会话列表两条新会话 + 新会话内的任务块与结果）+ sqlite 查询输出
- **失败处置**：先分清「应用坏了」还是「卡片过期」——会话创建口径看 `src-tauri/src/bot_chat/exec.rs`（标题前缀三档：📋 任务：/ ⏰ 定时：/ 📦 批量：）；前端触发看 `src/components/ChatPanel/ChatPanel.tsx` 的 `bot_execute_task` 调用。
- **缺口补验**：无实机卡：任务卡 🤖 与定时执行统一走新会话 —— 补验点：定时任务必须**真的到点跑**（把触发时间设到最近一分钟），跑完看列表是否 +1 条「⏰ 定时：」会话；只建定时任务不触发不算验过。

  5. 改某个模型条目的推理参数（如 temperature / max_tokens），保存后回聊天页发一句看是否按新参数走。
- **判据**：

  3. 【可审计】`"~/Library/Application Support/com.renshi.wmessage/bot.log"` 中两轮请求的 `llm.request` 事件 `provider` 字段分别为 `openai` 与 `anthropic`。
