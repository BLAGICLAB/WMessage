# WMessage 整体验收工作方案

> 版本：2026-10-30 首版
> 范围：`SPEC.md`「功能规格」六节全部 114 条功能条目（88 条主条目 + 26 条子条目）
> 配套：`docs/acceptance/matrix.csv`（功能 → 卡号 → 覆盖层追踪矩阵）、`docs/acceptance/cards-*.md`（逐条验收卡）、`tests-audit/audit_acceptance_matrix.py`（方案与代码对拍门禁）

---

## 〇、这份文档解决什么

wmessage 的 agent 侧在 2026-10-20 → 10-30 之间改了 584 个提交，功能规格攒到 114 条。
验收资产散在十余份文档里（`docs/realmachine-*.md` 六份、`docs/agent-audit-*.md` 两份、模块审计账本等），
每一份覆盖一个时间窗的改动，彼此有重叠也有空白——**没有任何一处能回答「这条功能到底验没验过」**。

本方案只解决三件事：

1. **把 114 条功能拆成可判定的验收项**，每条挂一张卡，卡上写死前置、步骤、判据、证据；
2. **把验收分层**：机器判的（门禁、单测）与人判的（实机）各归其位，谁执行、留什么证据、失败怎么处置写清楚；
3. **用一条门禁把「功能 → 卡 → 判据」对住**，防止方案与代码分家——卡片和代码分家时，执行者只能靠猜判断是「应用坏了」还是「文档过期」（既有 `audit_doc_claims.py` 已经为这件事栽过一次跟头，见附录 D-3）。

本方案**不重复**既有实机文档的卡面内容，但**每条功能仍各有一张卡**：
既有卡（如 `docs/realmachine-smoke-test-2026-10-25.md` 的 M75–M92）作为「历史证据」记在矩阵的
「既有卡号」列与卡片的「历史卡」行；本方案的卡是**唯一权威验收面**——判据一律重写，
不复用旧卡原文（变异报告已判 5 张旧卡口径需改，见 §9.2 第 3 条）。

## 一、验收口径：四层模型

| 层 | 名称 | 判定方式 | 执行者 | 证据物 | 失败处置 |
|---|---|---|---|---|---|
| **L0** | 门禁层 | 机器判 | 每次提交自动 | 退出码 | 当场修，不得带病提交 |
| **L1** | 模块层 | 机器判 | 每次 push / 验收前 | 测试报告 | 补测试或修实现 |
| **L2** | 实机层 | 人判（机器辅证） | 人工执行本方案卡片 | 截图 + 日志片段 | 开缺陷单，回填矩阵 |
| **L3** | 发布层 | 人工 + 出包验证 | 出包前 | 发版记录 | 阻断发布 |

### L0 门禁层（提交即跑）

命令与失败修法见 `docs/testing.md`。本方案只补充**验收视角的解读**：

| 门禁 | 在验收里防的是什么 | 验收判据 |
|---|---|---|
| `cargo clippy --all-targets -- -D warnings` | 「测试压根没被收集运行」——`nextest` 全绿但那个函数不在测试集合里 | clippy 缺失 = 该层判失败，不静默 skip |
| `tests-audit/audit_module_map.py` | 模块地图与真实文件分家 | 改架构文档后必须本地跑一遍 |
| `tests-audit/audit_doc_claims.py` | 实机卡里的审计事件名在源码里不存在 | 本方案的卡也受这条约束（见 §八） |
| `tests-audit/audit_file_size.py` | 存量大文件腐化 | 新文件 ≤1500 行 |
| `tests-audit/audit_acceptance_matrix.py` | **本方案新增**：功能条目漏卡 / 卡号重号 / 卡号指向不存在的功能 | 本方案自身与代码同生共死 |

### L1 模块层（自动化）

```bash
cd src-tauri && cargo nextest run        # Rust 全量
npm test                                  # 前端 vitest 全量
cargo test --test llm_integration         # mock LLM 全链路
cargo test --test task_chat_exec          # 任务卡执行聊天化
cargo test --test skill_e2e               # Skill DSL 端到端
cargo test --test memory_v2_degraded      # 记忆体 v2 降级
cargo test --lib memory::embed -- --ignored   # bge 真实推理冒烟（需 bge-small-zh-v1.5/）
```

**L1 的验收判据**：全绿，且**没有新增被 `#[ignore]` / `skip` 掉而没有说明的用例**。
跳过必须带原因注释——「Windows 上没判 ≠ 没事」。

### L2 实机层（主战场）

人工执行 `docs/acceptance/cards-*.md` 里的卡。每张卡的判据分三档：

- **可观测**：界面上看得见的状态、文案、计数、布局；
- **可审计**：日志/审计事件里出现指定事件名（判据写成 `a.b` 形事件名，由 `audit_doc_claims.py` 对拍源码）；
- **可核对**：产物目录、数据库、文件内容能核对（数量、哈希、行数）。

**只写可观测/可审计/可核对三种**——「体验更流畅」这类不可判的措辞不进判据。

### L3 发布层

出包前执行 `docs/acceptance/cards-90-windows.md`（Windows 专章）与便携模式相关卡。
门禁口径见 `docs/testing.md`「Windows 发版前最低验证」。

### 2.3 「负向卡」口径

对已退役/明写未做的项，同样出卡，但判据反向：条件满足时**必须观察不到**该物。
负向卡的价值是防复活——退役半年后没人记得它退役过，直到有人在 UI 上看到它。

## 四、验收环境与前置

### 4.1 平台

- **主线**：macOS（darwin，Apple Silicon）。自动化只在 macOS 跑，Windows 行为靠 L3 专章兜底（与 `docs/testing.md` 现状一致）。
- **专章**：Windows 10/11，只跑平台差异项（L3 卡集），不重复主线。

### 4.2 构建基线

- 验收一律用**当前工作区最新构建**，不混用历史 exe。
- 每轮验收记录 `git rev-parse --short HEAD`，写进回填记录；换构建必须重跑受影响的卡。

### 4.3 模型与凭据

- 至少配好两个厂商条目：OpenAI 兼容协议一个 + Anthropic 兼容协议一个（`SPEC.md` §3 双协议要求）。
- 厂商条目用**自己的 key**，不借用全局主 key（SPEC §5 密钥纪律）——验收时顺带验这条。
- 需要错误注入的卡（402 余额不足 / 401 / 429 / 5xx / 流内报错）用**可编排的 mock 网关**，不要真去撞上游。
- 思考段回灌相关卡需要 DeepSeek / Moonshot / MiniMax 三家中任一家带思考模式的模型。

### 4.4 本机依赖

`SPEC.md` §6 的「本机运行环境」卡列了三组依赖（Python 18 项 / Node 3 项 / 运行时 16 项）。
验收前用**设置页 → 机器人 → 本机运行环境**那张卡自查一次：五个文档硬依赖
（openpyxl / python-docx / python-pptx / pypdf / reportlab）必须全绿，否则文档族卡（D3c）整组判失败。

### 4.5 数据准备

| 场景 | 数据状态 |
|---|---|
| 干净库 | 首次启动、数据目录无 `wmessage.db` |
| 带数据库 | ≥30 张任务卡，覆盖：未排期 / 已排期 / 已完成 / 已归档 / 已软删 / 带子任务 / 带文件绑定 / 带标签 |
| 记忆体 | ≥20 条记忆（含 ≥2 条 lesson），触发一次 consolidation |
| 技能 | ≥2 个用户技能（一个启用、一个关闭），含一个带 `intents` 的 |

### 4.6 探针脚本

| 脚本 | 平台 | 用途 |
|---|---|---|
| `scripts/realmachine/smoke.sh` | macOS | 启停 / 静态面 / 退出清理 |
| `scripts/regression-probe.sh` | macOS | 回归卡的事件名与状态探测 |
| `scripts/regression-probe.ps1` | Windows | 同上 |
| `scripts/mutation-trace-funnel.sh` | macOS | 工具结果回灌漏斗（溢出转存） |
| `scripts/overflow-probe.sh` | macOS | 溢出文件落盘与回读 |

探针能替人验的：事件是否落账、文件是否落盘、计数是否对得上、进程是否清理干净。
**探针验不了的**：布局对不对、气泡宽不宽、浮窗滑不滑——那些必须人看。

## 五、执行批次与顺序

| 批次 | 内容 | 出口判据 |
|---|---|---|
| **B0** | L0 门禁：`bash scripts/test-fast.sh` | 退出码 0 |
| **B1** | L1 自动化：`cargo nextest run` + `npm test` + 四条集成测试 | 全绿，无无说明跳过 |
| **B2** | L2 实机主线（macOS）：按 D1 → D6 顺序逐域跑卡 | 每卡有结论与证据 |
| **B3** | L3 Windows 专章 | 专章卡全过 |
| **B4** | 收口：回填矩阵状态、登记缺口与豁免 | 矩阵无「未验」残留，或残留全部登记为已知缺口 |

**顺序理由**：D1（看板）是其余域的载体（任务卡是机器人执行的入口）；D2/D3a 是会话外壳；
D3b 的守卫卡需要 D3a 的聊天环境；D4/D5 依赖 D3c 的工具通道；D6 独立，可并行。

**B2 单域内部**建议顺序：先跑「已有实机卡覆盖」的条目（回归成本低、历史结论可比对），
再跑「本方案新开卡」的条目（无历史基线，需要更多判断时间）。

## 六、证据与回填规范

### 6.1 每卡一条记录

```
卡号：ACC-K-03
功能：SPEC 1-03 任务编辑浮窗
平台：macOS 15 / HEAD=a1b2c3d
时间：2026-10-30 21:10
结论：通过 / 失败 / 阻塞 / 跳过（附豁免号）
证据：docs/acceptance/evidence/2026-10-30/ACC-K-03-浮窗滑出.png
日志：docs/acceptance/evidence/2026-10-30/ACC-K-03-bot.log
缺陷：缺陷号（失败时必填）
备注：
```

### 6.2 证据存放

`docs/acceptance/evidence/<日期>/<卡号>-<短述>.<ext>`，允许入仓（缺陷定位需要），
但**单文件超 5MB 不入仓**，只留路径与说明。

### 6.3 日志取证

数据目录（macOS）：`~/Library/Application Support/com.renshi.wmessage/`（Tauri `app_data_dir()` + 标识 `com.renshi.wmessage`）；
便携模式下随 exe 走（`paths.rs` 的 `probe_dir`：exe 同目录可写则锚定 exe 目录，不可写回退 `app_data_dir` 并记 `data_dir_fallback`）。

```bash
# 卡片判据里写的审计事件名，直接在 bot.log 里查
grep -F "<事件名>" ~/Library/Application\ Support/com.renshi.wmessage/bot.log | tail -20
# 错误账本（WARN/ERROR 镜像，不被 Info 流水稀释）
grep -F "<事件名>" ~/Library/Application\ Support/com.renshi.wmessage/error.log
```

事件名在卡上写成 `a.b` 形，由 `audit_doc_claims.py` 对拍源码——**卡片与代码分家时门禁当场报**。

### 6.4 矩阵回填

每跑完一个批次，回填 `docs/acceptance/matrix.csv` 的 `状态` 列：
`未验` → `通过` / `失败` / `阻塞` / `豁免`。状态列是这份矩阵的核心产出，**空矩阵等于没验收**。

## 七、缺陷分级与豁免

| 级 | 判据 | 时限 | 处置 |
|---|---|---|---|
| **P0** | 核心链路不可用、数据损坏、密钥泄露、越权写盘 | 立即 | 阻断发布，当天修 |
| **P1** | 功能不达 SPEC 描述或绕过闸门 | 本轮验收内 | 本轮修完再进 B3 |
| **P2** | 体验偏差、措辞不符、文案过期 | 排期 | 记入缺口清单 |
| **P3** | 冗余/一致性建议 | 择机 | 可豁免 |

### 豁免流程

1. 在矩阵该行写 `豁免` + 豁免号（格式 `EX-<四位序号>`）；
2. 在卡上写明：豁免理由、**风险面**、**补验条件**（什么情况下必须回来验）；
3. 豁免**不允许覆盖 P0/P1**；
4. 豁免不写在源码注释里（AGENTS.md 硬性禁令：决策记录只进 DEVLOG）。

## 八、方案自身的门禁

`tests-audit/audit_acceptance_matrix.py`（新增，已进 `scripts/test-all.sh`）查五件事：

1. **功能条目数对齐**：矩阵行数 == `SPEC.md`「功能规格」节解析出的条目数（88 主 + 26 子 = 114）；
2. **每条功能有卡**：矩阵每行的卡号非空，且能在 `docs/acceptance/cards-*.md` 里找到对应标题行；
3. **卡号唯一**：一个卡号不能被两条功能共用；
4. **卡 ↔ 功能双向对住**：卡文件里标注的 SPEC 编号与矩阵该行的编号一致（防张冠李戴）；
5. **判据里的事件名真实存在**：卡上出现的 `a.b` 形事件名必须在源码里存在（复用 `audit_doc_claims.py` 的扫描器与豁免名单）。

第 5 条复用现有实现，不另立一套事件名规则——两套规则必然漂移。

## 九、当前覆盖缺口与补齐计划

本节是盘点结论（2026-10-30，HEAD `d424c992`）。逐条缺口见 `docs/acceptance/matrix.csv` 的「缺口说明」列。

### 9.1 覆盖总账

口径以 `docs/acceptance/matrix.csv` 的「历史覆盖度」列为准（机器可核，与门禁同源）：

| 覆盖度 | 条目数 | 含义 |
|---|---|---|
| **全** | **29** | 有专卡直接对该条行为面下判据，且口径与现行实现一致 |
| **部分** | **38** | 有相邻卡 / 抽样卡触及该条的一半，或旧卡口径已随 10-26 之后的改动过期 |
| **无** | **47** | 全库无任何针对该条行为面的专卡（其中 2 条是负向卡、1 条由 L0 门禁承担） |
| 合计 | **114** | — |

**47 条无历史卡**的分布：

| 类别 | 条数 | 例子 | 为什么之前漏了 |

### 9.2 三条硬约束（本方案的成立前提）

1. **验证断层**：最后一次实机复验的源码点是 `16fa2eac`（2026-10-26 02:35），其后到 HEAD 有 **146 个提交未经任何实机卡片覆盖**。
   这批提交集中在 agent 循环（ask_user 等待环、check 薄片等待、`/stop` 可打断、SSE 攒批、pack 心跳、子 agent 终态落库重试、前端回灌状态机）——**恰好是静默失效风险最高的一段**。
   → 本方案的 B2 批次必须以当前 HEAD 完整重跑，不接受「沿用旧结论」。
2. **Windows 面几乎全空**：W10–W12 未跑、W04–W06 未跑、W01–W09 只在 10-22 跑过一次。

### 9.7 写卡时查出的「SPEC 与实现不符」（本方案最值钱的产出）

| # | SPEC 口径 | 实现实际 | 处置 |
