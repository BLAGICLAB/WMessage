# Rust Bot 全面审计 · 批次 4：本地 HTTP API Server（2026-08-28）

范围：`api_server.rs`（生命周期/EventHub/并发）、`api_handlers.rs`（路由/CRUD/SSE/tauri 命令）、
`api_auth.rs`（token/鉴权）、`api.rs`（TaskStore 数据层），上下文核对 `db.rs` / `error.rs` /
`lib.rs` / `mutation.rs`。单代理探索 + 全部 P1/P2 人工源码复核（本报告行号均已核对）。

## 结论

**无 P0。** 绑定只限 127.0.0.1、鉴权覆盖除 health 外全部端点（含 SSE 与未知路径）、
ct_eq 常数时间比较、token 0600 且不进日志、body 1MB 硬上限、worker 上限 64 + panic 拦截、
无 CORS 头（DNS rebinding 无利用面）——主干安全设计到位。

## P1（处理情况）

### P1-1 accept 循环级 slowloris（记录残留，无法廉价修复）
- `api_server.rs:159` `recv_timeout(400ms)` 是「单次读不活动」超时，tiny_http 在 recv 内部
  **顺序**读完一条连接的 header 才产出 Request：每 <400ms 滴注 1 字节的连接可永久占住
  accept 循环，全部端点（含 health）饿死。171-172 行注释声称的「15s 超时防 slowloris」
  只作用于 Request 产出之后的 handler 阶段——**过度声称，注释已修正**。
- 不修的说明：tiny_http 不暴露 per-connection 读超时，彻底修需换 HTTP 栈（立项）。
  缓解面：仅回环、需本机执行能力；即便占住 accept 也过不了鉴权（但 DoS 本身成立）。
- 本批改动：修正注释 + 此残留条目。

### P1-2 API 写路径 read-modify-write 无锁（已修：API 侧串行化）
- 证据：`update_task`（api_handlers.rs:533-544）/ `delete_task`（675-686）/
  `create_task` 的 max_order（448-455）都是 load → 改 → upsert 两段式，
  两把 DB_WRITE_LOCK 之间窗口内并发 API 请求（MAX_WORKERS=64）互相用旧快照整行覆盖。
- 修法：进程级 `API_RMW_LOCK`，create/update/delete 三个写 handler 全程持锁——
  API 自身并发写串行化（P2-3 的 max_order 竞态一并消除）。
- **残留**：跨路径（API vs UI/bot）的 lost-update 仍属已立项的「19 列整行替换」架构项，
  本锁不覆盖（UI/bot 不经过它），不重复报。

### P1-3 死 SSE 连接占位不清，安静期内新连接被 503（已修）
- 证据：`MAX_SSE_CLIENTS=32` 看 `clients.len()`（782）；死连接的 SyncSender 只在
  下一次 broadcast 的 try_send 失败时才移除（api_server.rs:105-106）。32 个客户端
  先后断开且无任务变更 → 第 33 个连接起全部 503，直到下次广播才自愈。
- 修法：clients 条目携带 writer 存活令牌（`Weak<()>`，writer 线程持 Arc）；
  sse_connect 注册前先 `retain` 收割尸体，再判容量。

## P2（处理情况）

- **P2-1 body 阶段 slowloris 只记日志不杀连接**（记录残留）：15s watchdog 超时后 worker
  续跑到客户端断开，1 字节/分钟可永久占 1 个 worker 名额，64 个即耗尽。本机威胁面可接受。
- **P2-2 HttpStartFailed 死变体**（已修）：api_start 现在显式 map 到
  `CommandError::HttpStartFailed{port,reason}`，前端 code 分支可用。
  （PortInUse/AuthMissing/AuthInvalid/PayloadTooLarge 仍是死变体，保留待错误体系统一时清理。）
- **P2-3 create 的 max_order 竞态**（已修）：随 P1-2 的 API_RMW_LOCK 一并消除。
- **P2-4 note/file_path 存未 trim 原文**（已修）：create_task 的 note/files、
  update_task 的 file_path 统一 trim 后存储。
- **P2-5 500 响应回吐 DB 错误原文**（已修）：8 处 `json_err(500, &e)` 改对外统一
  `"internal error"`，原文过 escape_for_log 进 api.log（list/get 补上 log 参数）。
- **P2-6 token 轮换中途失败窗口**（已修）：api_stop 失败时回滚旧 token 文件，
  与 start 失败的回滚对称。
- **P2-7 API 写操作不进结构化审计 bot.log**（记录缺口）：变更只写 api.log 文本行；
  handler 无 AppHandle，结构化审计需穿 store 层，留待后续。非注入问题（转义已到位）。
- **P2-8 api_start 双发竞态**（已修）：检查与写入改为同一把锁内完成（持锁跨过 start_api），
  并发 invoke 不再出现「第二个报端口占用但服务其实已起」的误导错误。
- **P2-9 update_task 对空白 title 静默忽略**（已修）：显式传了 trim 后为空的 title → 400，
  与 create 语义对齐（未传仍是不动）。

## 已确认无问题（防爆雷清单）

- 只绑 127.0.0.1；端口固定 4763，冲突报错不静默换端口。
- 鉴权覆盖除 health 外全部端点（含 SSE、404/405 未知路径先过鉴权）；ct_eq 常数时间；
  token 0600；token 不进任何日志/错误响应；轮换失败有回滚（本批补上 stop 失败分支）。
- body `take(1MB+1)` 硬截断，Content-Length 撒谎/chunked 均不吃内存。
- 无路径遍历（id 仅内存等值匹配，path 不解码、不碰文件系统）；
  `%0A` 不解码所以访问日志不可注入；query percent-decode 边界正确。
- 限流在鉴权之后（401 风暴不耗合法预算）；health 免鉴权免限流只回静态 JSON。
- 输入校验到位：title 非空 ≤200、note ≤5000、due ≤30、tags ≤10×30、status 白名单；
  serde 强类型，JSON 类型混淆一律 400。
- SSE：事件 id 持久化跨重启单调；重放/在线按 id 去重；writer 全量注册、
  stop+join 5s 超时+泄漏审计；单客户端队列 256 有界、广播 try_send 不阻塞。
- 退出清理顺序正确（API→Skill→Python），死服务被 api_status 活性检查识别清尸。
- 写库走 DB_WRITE_LOCK 与 UI/bot 同锁；API 变更经 MutationOrigin::Api 只合并不回写。
