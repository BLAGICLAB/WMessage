## P0（已修）

### P0-1 同名 Skill 跨会话顶号：先跑的一方安全闸全失
- 证据：`bot_skills/state.rs:79` SKILL_RUNS 以**技能名**为键；
  `runtime.rs:69` `runs.insert(meta.name, run)` 直接覆盖；50-59 的「切技能清理」
  只处理**同会话**的其他技能（`r.session_id == session_id` 且 `*n != meta.name`），
  对「别的会话正在跑同名技能」完全不设防。
- 触发：会话 A 的 Skill X 运行中，会话 B `use_skill X`（或 pre-step 路由命中同名技能）。
- 后果：A 的 run 被整个顶掉。此后 `skill_on_step`/`skill_on_step_post`（runtime.rs:156-162、
  191-196）按 session 过滤找不到 A 的 run → **A 的步数熔断、超时熔断、回滚动作记录、
  skill_finish 收尾全部静默失效**。
- 修法：start_skill 插入前检查——同名技能在**其他会话**处于 Running/Paused → 拒绝启动
  （报错给模型/用户，等对方结束）。纯函数 `skill_conflict_with_existing` + 单测。

### P0-2 并行会话的流式输出串台
- 证据：`bot_model_loop.rs:611/615/628/635/749` 的 `bot-chat-delta`/`bot-think-delta`/
  `bot-tool`/`bot-tool-name`/`bot-tool-done` payload **不带 sessionId**；`emit_to("widget")`
  单窗广播。`CHAT_RUNNING`（bot_chat.rs:313）是 per-session 锁，两个不同会话可并行跑。
  前端 `ChatPanel.tsx:420-510` 六个监听器一律追加到「最后一条 streaming 消息」，无会话过滤
  （对比 `bot-confirm` 带 sessionId 且前端按会话过滤，bot_slash.rs:240 + ChatPanel.tsx:565）。
- 后果：会话 A 的模型输出/思考/工具行串进会话 B 正在显示的气泡。
- 修法：emit_stream 统一给 payload 注入 `sessionId`；`bot-skill-failed`（bot_chat.rs:512）同补；
  前端六个监听器按 `payload.sessionId === sessionIdRef.current` 过滤。

## P1（已修）

### P1-1 干净 EOF（无 [DONE]/finish_reason）时残缺 tool_calls 被当完整回复执行
- 证据：`bot_model_loop.rs:581` 流循环在连接正常关闭（`None`）时无错退出；
  `finish_reason` 解析了（365-372）但主循环从不读；`is_done` 只 `continue`（604-605）。
- 触发：中间代理/网关在 tool_call arguments 流到一半时干净关连接（idle cut）。
- 后果：残缺 arguments 靠 `parse_args` 失败落 `Value::Null` 侥幸兜底（工具报缺参数）；
  content 侧半截话当完整答案返回。无显式防线。
- 修法：跟踪 `saw_done_or_finish`；流结束（非 /stop）未见到 → 有 tool_calls 则整条报错
  不执行；无 tool_calls 且已有正文则追加「响应可能被截断」提示；空响应报错。

### P1-2 UTF-8 多字节字符跨 TCP chunk 产生 U+FFFD 替换符
- 证据：`bot_model_loop.rs:599` 对每个网络 chunk 独立 `String::from_utf8_lossy`。
- 后果：中文场景必然偶发 ``。正文只是乱码；**arguments 里的 `` 是合法 UTF-8，
  JSON 仍合法，工具拿损坏参数真实执行**（如建出标题含 `` 的任务卡）。
- 修法：字节缓冲 `Vec<u8>`，按 `b'\n'`（不会出现在多字节序列内）切行后整行 decode。
  抽纯函数 `drain_sse_lines`，单测覆盖「多字节字符跨 chunk 无 U+FFFD」。

### P1-3 200 流内错误载荷被静默吞 → 空白回复
- 证据：`parse_sse_chunk` 对无 choices 的 JSON 返回 None（331-335），主循环跳过；
  旧测试把「`{"error":...}` 应被忽略」固化为预期（1094-1101）。
  OneAPI 类网关会在 200 流内发 `{"error":{...}}`。
- 修法：`ParsedChunk` 加 `error` 字段；主循环收到 → 审计 + 报错（不再返回空白）。
  旧测试改写为「错误必须显式冒出」。

### P1-4 429/5xx/网络错误零重试
- 证据：`bot_model_loop.rs:538-548/551-563` 任何失败直接 Err。429 限流与 401 同等待遇。
- 已确认无重放风险：重试发生在流式产出开始前；已执行工具不会因重发请求而重放。
- 修法：`MAX_LLM_ATTEMPTS=2`，429/5xx/发送失败重试一次（1.5s 退避），每次记 `llm.retry` 审计。
  纯函数 `is_retryable_llm_status` + 单测。

### P1-5 聊天主路径无上下文预算，长会话直接 400
- 证据：`bot_chat.rs:587-593` 全量透传；全库无 tokenizer/估算。工具循环内 msgs 只增不减
  （extract_document 单页上限 6 万字符 × 最多 50 调用 × 50 轮，内存态理论上 MB 级）。
  超限路径 = `LlmApiError` 400。
- 修法：入口侧字符预算 `HISTORY_BUDGET_CHARS=100_000`（中文 ~1 token/字符），最旧的先丢、
  永远保留最后一条，丢弃时记 `chat.history_truncated` 审计。纯函数 `truncate_chat_history` + 单测。
  **已知残留**：工具循环内的内存态增长不设预算（工具结果各自有截断上限兜底，
  极端长任务仍可能 400）——列入后续观察，不在本批次做循环内截断（有拆散 tool 配对风险）。

### P1-6 历史图片每一轮对话重复 base64 内联
- 证据：`bot_chat.rs:577-593`「最近两条 user 消息」的图片**永不失效**——一张图在之后
  每一轮对话都重新内联（每张 ≤3MB × 每条 ≤4 张 ≈ 单请求最多 ~32MB base64）。
- 修法：改为「最后 3 条消息内的 user 消息」才附图——保住「发图→追问一轮」的设计意图，
  第二轮追问起图片降级为路径文本。纯函数 `image_attach_indices` + 单测。

## 已确认无问题（防爆雷清单）

- SSE `[DONE]` 为 trim 后精确匹配；`data: [DONE]extra` 会 JSON 解析失败被丢弃（fail-safe）。
- 行缓冲存在，chunk 切断 `data:` 行不出问题；`: keep-alive` 注释行正确跳过。
- tool_calls 按 index 归位（非顺序 append）；id 只置首次、迟到 id 能补上；args 跨 delta 拼接正确。
- 流式 chunk 错误（RST/超时）整轮 Err，不执行半截 tool_calls。
- think 标签跨 chunk 拆分（含未闭合冲刷）正确且有单测；think 不进 msgs、不进持久历史；
  DB `thinking` 列与回传的 `ChatMsg{role,content}` 分离，无上下文污染。
- tool_calls ↔ tool 配对完整（含 /stop 占位回填、熔断路径 msgs 随 return 丢弃不持久化）；
  soft_warn/fail_hint 推迟到 tool 响应全部回填后注入（防 400）。
- system prompt 不被截断；动态段后缀追加、轮内稳定（prompt cache 友好）；
  用户/任务卡内容走 user 消息而非 system；技能正文属用户自控内容，边界标记存在。
- bot_plan 是纯提示词层（无只读约束可绕过），计划不持久化、不进对话历史；
  步数 ≤8、Replan ≤2 硬上限有效。
- API key 只出现在 Authorization header；非 200 body 截 300 字进 CommandError 但不进审计日志；
  `audit_event!` 结构化路径全量转义（audit.rs:41-45）。
- 工具结果截断全部按 `chars()`（UTF-8 边界安全）；持久历史 2000 条头丢不破坏配对（历史无 tool 消息）。
- 全局静态状态除 SKILL_RUNS（P0-1 已修）外均按会话/任务正确隔离
  （STOP_REGISTRY/CONFIRMS/CHAT_RUNNING/EXEC_RUNNING/SCHED_RUNNING/exec_steps::PENDING）。
