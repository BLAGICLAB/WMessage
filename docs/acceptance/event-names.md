# 审计事件名总表（卡片判据可引用的白名单）

> **抽法**：真实审计发射点的**事件名参数位**（`audit_event!` 宏、`write_event` / `write_event_with_error`、
> `emit_recorded` 统一信封出口、`frontend_event_report` 前端上报）∪ 生产源码里出现的 dotted 字面量，
> 再滤掉三类明显不是事件的：文件后缀、域名/TLD、DOM API 前缀（`document.` / `window.` / `console.` …）。
>
> 为什么不用「全源码扫 dotted token」：那会把 `document.write`、测试夹具名、文件名一并收进来——
> 白名单一旦有假阳性，写卡的人就会拿它当「可以写的名字」，把假阳性写进判据。
> 为什么不用「只取发射点」：有些事件的落点是 `format!` 拼串或别的 helper（如 `skill_step_fail`），
> 只认发射点会漏收真事件，而漏收的代价是卡里写了白名单外的名字、门禁当场拦下。
>
> 共 250 条。表外的名字有两种合法用法：运行时拼出的（`前缀.{动作}` 形态，源码里能找到 `前缀.{`）、
> 以及中文期望文案（按 `format!` 运行时拼出，按既有约定不进对拍闸）。

## 补充：源码里以 `format!` 拼串出现的真事件

> 这几条不在上面的自动抽取里（拼串不是字面量参数位），但确实是审计事件，SPEC 也有点名。

- `skill_step_fail` —— 以 `format!` 拼串出现在 `bot_skills/runtime.rs` 的失败行里（后面接 ` | name: …`）
- `mcp.builtin_materialized` —— 以 `format!` 拼串出现在 `bot/mcp/builtin.rs` 的内置材料化事件里
- `builtin_skill_purge_failed` —— 内置技能退役清理的逐项审计事件
- `hallucination_guard` —— 守卫**首次**拦下（第二次是 `hallucination_guard.repeat`）；源码 `bot_model_loop/guard.rs` 里事件名与参数位不同形，自动抽取漏收
