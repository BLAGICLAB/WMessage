## 一、功能实测（真服务 + curl，18 项全过）

方法：`start_api` + MemStore 起真服务（127.0.0.1:48899），curl 逐端点实测。
（临时 example + lib.rs 临时 pub 已清理，测试基线复验：lib 490 绿 / tsc 零错。）

| 项 | 结果 |
|---|---|
| GET /api/health 免鉴权免限流 | ✅ 200 `{"ok":true,"service":"wmessage-api"}` |
| 无 token / 错 token | ✅ 均 401 `unauthorized` |
| 空 title / 非法 JSON | ✅ 均 400 |
| 创建 / 列表 / 单查 / 更新 | ✅ 201/200，字段往返正确 |
| 不存在 id / PATCH / 未知路径 | ✅ 404 / 405 / 404 |
| SSE 在线推送 | ✅ 连接即收 `connected`（带 lastEventId），POST 后实时收 `tasks-changed`（带事件 id） |
| SSE 断线重放 `?since=N` | ✅ 只补发 id>N，不重发旧事件 |
| body >1MB | ✅ 413 |
| 限流 120 次/分钟 | ✅ 超限回 429 |
| DELETE 软删 | ✅ deletedAt 置位；列表默认排除回收站（`?status=deleted` 可查）；GET by id 不过滤回收站（与列表语义一致的设计，观察项） |

**实测澄清的一个非 bug**：PUT 带客户端伪造的过期 `expectedUpdatedAt` 仍 200——
正确行为。API 的 RMW 基线由 handler 自己在锁内取（`api_handlers.rs:594`，
基线=本次 load 快照的 updated_at），客户端传的基线字段被忽略；409 只在
load→upsert 之间被其他写者（bot/前端）插队时触发，db 层有单测覆盖
（`upsert_expected_baseline_rejects_stale_write`）。

## 二、审计发现

### P1（2 项，都围绕 accept 循环，读超时 patch 管不到）

**P1-1 accept 循环同步等待 worker，慢请求可冻结全服务 15s/次**
- `api_server.rs:207-229`：spawn worker 后 accept 线程 `done_rx.recv_timeout(15s)` 同步等结果。
- 后果：任一 handler 超 15s 期间新请求全部排队（吞吐降为 1 req/15s），本机单连接轮替即可持续不可用；`api_stop_impl`（`api_handlers.rs:1017-1021`）join 最坏卡 15s 且全程持 `state.0` 锁，连带阻塞 `api_status`。
- 该等待的唯一收益是把 worker panic 消息带回 accept 线程记日志。
- 修法：`on_error` 包 Arc 传入 worker 自行记录，accept 循环不等待（15s「超时」语义本来就是假的——worker 超时后续跑）。

**P1-2 body 阶段 slowloris 绕过全部现有缓解**
- `api_handlers.rs:238-249`（`read_body_limited`）+ `api_server.rs:218-228`。
- vendor patch 的 30s 读超时是单次 read syscall 级：发完 header 后以 <30s 间隔滴注 body，每次 read 都按时返回，worker 永久存活（15s handler 超时不杀 worker）；64 个占满 MAX_WORKERS → 全员 503，且每连接还在 tiny_http 无上限 TaskPool 钉一个读线程。
- 修法：`read_body_limited` 加总时长 deadline（如整体 35s，或按 Content-Length 预拒绝）；彻底修复归换 axum 立项。短期先把 patch 注释里「与 15s handler 超时语义协调」的说法改正——该协调不成立。

### P2（9 项）

| # | 位置 | 问题 | 修法 |
|---|---|---|---|
| 1 | `api_handlers.rs:949-954` | `api_start` 对已死服务误报成功（不查 `handle.is_finished()`，accept 线程 panic/recv_error 死亡后端口没人听仍返回 Ok） | 复用 `api_status`（:1043-1055）的活性检查 + 尸体清理 |
| 2 | `api_auth.rs:40-49` | token 文件先 write（umask 0644）后 chmod，中间有可读窗口；存量 0644 文件永不补 chmod | `OpenOptions` + `.mode(0o600)` 创建即收紧；读取时发现权限过宽补 chmod |
| 3 | `api_server.rs:94` | 事件 id 落盘非原子：崩溃留半截文件 → 重启 id 归 0 → 客户端 Last-Event-ID 去重静默丢全部新事件（正是该功能要防的事故） | 换用 `db.rs:139` 现成的 `atomic_write`（tmp+rename），一行 |
| 4 | `api_handlers.rs:594/746` + `db.rs:983` | T1-1 基线空洞：老行 `updated_at` 为 NULL 时基线是 None → 跳过比对，最需要防 lost-update 的老行无保护；updated_at 毫秒粒度同值冲突漏检（极低概率，备查）；MemStore::upsert 忽略基线，API 409 路径无集成测试 | update 路径对 NULL 行用「行存在性」作基线；补一条 API 层 409 测试 |
| 5 | `api_handlers.rs:1075/1090` | `api_rotate_token` 检查与操作非原子：窗口内用户并发 stop，rotate 会把服务重新拉起 | rotate 全程持 `state.0` 锁，或合并为持锁的 `api_restart` |
| 6 | `api_handlers.rs:238-249` | `read_body_limited` 把读 IO 错误（含 30s 超时）和超 1MB 都回 413 | 读失败回 408/400，超限才 413 |
| 7 | `api_handlers.rs:832` | `?since=abc` parse 失败静默按全新连接处理，客户端不知丢窗口 | 非法 since 回 400；history 环形缓冲 1000 条溢出缺段至少文档注明 |
| 8 | `api_handlers.rs:643-672` | `filePath` 只 trim 不限长（title/note/due/tags 都有 over_limit），单字段 900KB 可进库 | 与 bot 侧对齐补上限 |
| 9 | `api_handlers.rs:1058` | `api_status` 每次都 `load_or_create_token`，从未开启 API 也会生成 token 文件 | 未启用时不读 token（或前端不展示 disabled 态 token） |

### 已复核到位（不再重复修）

ct_eq 恒定时间比较、token 0600 权限、API_RMW_LOCK、SSE Weak 尸体收割、
T1-1 409 接线（含 skip_serializing 防前端脏基线）、读超时 patch（SSE upgrade
