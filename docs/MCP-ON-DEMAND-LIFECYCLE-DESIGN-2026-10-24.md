# MCP 外部服务器：按需启停（静默待命 → 调用期拉起 → 调用完回收）

> 2026-10-24 · 现行实现口径见 `SPEC.md`「MCP 外部服务器」条。
> 本文只写「为什么这么切」与「哪些坑踩过」——代码结构与判据以源码为准。

## 一、为什么要改：开关一开就吃内存

原先的语义是「**启用 = 连上**」：设置页打开启用开关 → `reload_from_config`
给每台启用的服务器 spawn 一次子进程 → initialize 握手 → 拉工具清单 →
**一直挂着，直到用户关掉开关或退出应用**。

问题在于 stdio 服务器是真进程：`npx` / `node` 起的 MCP 服务器常驻 80–150 MB
（第三方 npm 包 + 它自己的依赖树）。装十台服务器 = 十份常驻；多开几个会话
（每会话一份）就是几十份。**大部分服务器在绝大部分时间里根本没人调**——
它们只是「在列表里挂着」，等着某次模型恰好要用它。

用户侧的观感就是：打开一个 MCP 服务器开关，机器风扇转起来、内存掉一截，
而他可能整个下午都没让模型碰过那台服务器。

## 二、业界怎么做（调研）

| 客户端 | 做法 | 出处 |
|---|---|---|
| Claude Code / Cursor / Claude Desktop | **启动即连、常驻到退出**（问题的来源） | mcp.avelino.run《MCP servers are draining your hardware》 |
| VS Code（Copilot Chat） | `chat.mcp.autostart`：可配成**按需启动**——提交聊天消息时才启动需要的服务器；首次启动后弹信任确认 | code.visualstudio.com/docs/copilot/customization/mcp-servers |
| mcp CLI proxy | **lazy 初始化**：`tools/list` 触发一次连接 → 发现工具 → 缓存 → **空闲的后端立刻关掉**（工具仍可见）；`tools/call` 命中已断开的后端时透明重连。另加**自适应空闲回收**（按使用频率分 hot/warm/cold 三档超时） | 同上 |
| rho 引擎 | `lifecycle: "lazy"` + `idleTimeout`（默认 600s）：**启动时不 spawn 子进程**，元数据缓存在 `mcp-cache.json`；调用时透明拉起；空闲超时后回收 | rho 引擎文档 |

共同点：**把「工具元数据」和「活连接」拆开**。工具清单是一次性的发现结果，
落盘缓存即可；活连接只在真正要调用的那几秒里存在。

mcp-proxy 那篇里有一句是本次改造的直接依据：

> Don't connect at startup. Wait until the user actually needs a tool.
> **Cache tool lists. You don't need a live connection to advertise tools.**

## 三、本次的口径

### 3.1 三态槽位

```
        配置对齐（开关打开 / 启动 / 配置变更）
                 │
                 ▼
        ┌─────────────────┐   工具清单未知 → 按需发现一次
        │  Idle 静默待命  │ ─────────────────────────────┐
        │  （没有进程）    │                              │
        └─────────────────┘                              ▼
                 ▲                        connect → list → disconnect → 落盘快照
                 │                                      │
                 │                              ┌───────▼────────┐
                 │        调用结束即回收         │  discovering   │
                 └──────────────────────────────┤  （发现中）    │
                                                └───────┬────────┘
                                                        │ 失败
                                                        ▼
                                                  ┌───────────┐
                                                  │ Down 失败 │（冷却 10 分钟）
                                                  └───────────┘
```

- **Idle（静默待命）**：已启用、工具清单已知、**没有进程在跑**。
  打开启用开关 = 进这个状态，**一个子进程都不启**。
- **Connected（活连接）**：只在一次工具调用期间存在（外加发现过程）。
- **Down（失败）**：连接 / 发现失败。进 10 分钟冷却——没有冷却的话，
  一台坏服务器会让**每一轮对话**都去连一遍（连接超时 10s 起步），整轮提问被拖死。
  冷却期内面板照常显示错误；用户手动开关 / 改配置 / 点「工具」即解除。

### 3.2 工具清单的可见性（关键的一环）

模型要看得见工具的名字与参数 schema 才会调用它。而 schema 来自
`tools/list`——那需要一条活连接。「连着才看得见」与「看得见才连」互为死锁，
所以两者必须解耦：

- 发现一次工具清单 → 落盘到 `<数据目录>/mcp-tool-cache.json`
  （按服务器 id 存「配置指纹 + 工具清单」）。
- 之后**没有连接**也能把工具挂进主 agent 的清单（`manager::mounted()` 认 Idle 槽）。
- 快照的有效性由**配置指纹**判定：改了命令 / 参数 / env / url / 超时 → 指纹变 →
  快照作废 → 重新发现。（指纹认 env/headers 这两个机密字段——它们在
  `Serialize` 里被 `skip_serializing` 剥掉了，用序列化值算指纹就看不见它们。）

### 3.3 发现时机

| 时机 | 触发 | 说明 |
|---|---|---|
| 主 agent 进模型循环前 | `manager::ensure_tools_known` | 快照缺失的启用服务器才连一次；**子 agent 不参与**（工具面是静态白名单，不挂 MCP 工具） |
| 设置页点「工具」 | `mcp_server_tools` | 用户主动要看清单 = 显式重试（解除冷却） |

发现 = **连上 → 列工具 → 断开**（连完就断，工具清单已经拿到）。

### 3.4 调用期启停

```
call_tool:
  取该服务器的调用闸（同一台服务器的并发调用串行化）
  → ensure_connected（此刻才 spawn 子进程）
  → 带超时调用
  → retire：停进程树 + 槽位退回 Idle（工具清单留着）
```

- 同一台服务器的并发调用**串行**：活连接一次只服务一个调用方（stdio 连接本来
  也只能这样）；并行调用排队即可，不丢请求。
- 进程**不跨调用存活**——这是「按需启停」与原先「懒重连」的分水岭：
  懒重连是「断了再连」，按需启停是「没调用就不连」。
- 停法沿用既有停止阶梯（SIGINT → 100ms → SIGTERM → 400ms → SIGKILL + 回收
  脱离进程组的子孙）。**没有改成「关 stdin 让它自己退」**：那条路要靠 rmcp
  释放传输才发生，而释放传输在阶梯之后——先关 stdin 的话，服务器自己退了，
  它的子孙就脱离进程组、阶梯再也收不到（孤儿）。阶梯优先是有意的。

## 四、踩过的坑

1. **SIGINT 会打出 KeyboardInterrupt 回溯**（Python 桩）。按需启停下每次调用
   结束都要停进程，那段回溯会挤掉 stderr 环形缓冲里的启动诊断行。
   环形缓冲保留「尾部 20 行」，回溯约 8 行——两三次调用就把真正的启动诊断顶掉了。
   **判据**：启动诊断的价值在「连不上时看尾巴」，而连接失败那条路上没有回溯
   （那才是它要救的场景）；且每次 spawn 前环形缓冲会被清空（上一次的回溯不留）。
   实测把 e2e 用例的 stderr 断言挪到调用之前即恢复。

2. **函数名登记簿是进程级的**：同前缀同工具名按序消歧（`mcp_echo_echo` /
   `mcp_echo_echo_2`）。新增 e2e 用例若也用 `echo` 这个服务器名，会跟老用例
   抢同一个名字，老用例的精确断言就飘了。新用例的服务器名要**互不相同**。

3. **`reload_from_config` 原来会连接**——改成「只对齐槽位、不启进程」后，
   「打开开关不启子进程」这条判据没法在原方法上直接测（它要 AppHandle）。
   拆出 `apply_config(&servers, &cache)`（无 IO / 无 AppHandle）后，
   单测可以直打这条判据。

## 五、实机验收判据

单测能证明「槽位状态对」，但「进程到底起没起」要看地面真相。

| # | 场景 | 判据 |
|---|---|---|
| A | 打开启用开关 | 进程表里**没有**该 MCP 服务器的进程（`ps` 按命令行特征查）；面板状态点为「静默待命 / 待发现工具」 |
| B | 面板可见 5 分钟（无人调用） | 进程表里依然没有它；内存占用不涨（对比开关前后） |
| C | 让模型调用它的工具 | 调用**期间**能看到该进程（`ps` 命中）；调用结束后进程消失 |
| D | 连续调用两次 | 两次都能成功；两次之间进程确实起过两次（按需启停 = 不跨调用存活） |
| E | 停用开关 | 进程表里没有它；模型清单里它的工具消失（下一轮） |
| F | 断网/改坏命令后启用 | 面板显示失败原因；**连续多轮对话不再卡 10s**（冷却生效） |
| G | 重启应用（不重新配置） | 模型清单里仍有它的工具（盘上快照），且**没有进程被拉起** |

**B 与 G 是这次改造的核心判据**——它们直接对应「开关一开不启进程」与
「工具可见性不依赖活连接」两条新不变式。A/C/D 是「按需启停」的行为面，
E/F 是失败面（冷却 + 摘槽）。

## 六、不做的（留给将来有第二个调用方时再说）

- **空闲超时回收**（业界常见档位：hot 5min / warm 3min / cold 1min）。本次口径是
  「调用完即关」，比超时更彻底；等真出现「一轮里连续调十几次同一台服务器、
  每次都付一遍 spawn 代价」的实测反馈，再加超时档位。
- **按服务器粒度的启停策略配置**（有的服务器想常驻、有的想按需）。开关本身就是
  这个粒度，再加一层配置是重复抽象。
- **HTTP 传输单独一套生命周期**：HTTP 没有本地进程，但会话建立仍有成本；
  本次与 stdio 同口径（调用期连、调用完断），少一条分支、少一处心智负担。
