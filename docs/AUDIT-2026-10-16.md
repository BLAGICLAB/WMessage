## 二、第一轮：程序模块新代码 + 挂件退役残留

### P1-1 确认弹窗有两个呈现者，同一请求弹两次（`f807de9`）

ChatPanel 重设计给聊天窗加了一套 `bot-confirm` 监听，而 `ConfirmMap` 一直在挂。
两者同窗常驻（聊天窗只切 `hidden` 不卸载），于是同一请求弹两个窗：ConfirmMap
的 `z-[100]` 在上、用户在那里答完，ChatPanel 的 `z-50` 残影还留在下面；点它会
调 `bot_confirm_response` → 后端 `take_confirm` 找不到请求 → 前端
`handleCommandError(..., { silent: true })` **静默失败**，用户以为点了其实没生效。
`confirmReq` 也不随会话切换复位，切走会话后旧弹窗继续挂着。

修法：**单一呈现者**。删掉 ChatPanel 的监听 / state / 弹层，保留 ConfirmMap
（它在任何视图下都可见，聊天窗里的弹窗在非聊天视图里根本看不见）。`file_access`
的三选一（允许一次 / 始终允许该目录 / 拒绝）搬进 ConfirmMap——否则删掉聊天窗那
份就丢了「始终允许该目录」的入口。反向裁掉 ChatPanel 的会话隔离语义是有意的：
ConfirmMap 无会话过滤，别的会话的确认照样弹，能力没缩水。
新增回归锁：ChatPanel 测试断言它不再 listen `bot-confirm`。

### P1-2 程序脚本路径无穿越闸（`bd9d48f`）

`apps::run` / `preflight_script` 直接 `app_dir.join(script_rel)`，而 `script_path`
从 `apps_create` / `apps_update` 命令进来只有 `validate_app_id` 把关，没有校验
路径形态。契约上它恒为 `app.py`（`docs/APP-DEV-CONVENTIONS.md` §2），但命令层
收 `../../x.py` 或 `/etc/passwd` 都会照单执行——把 app 目录外的任意文件读走当
Python 跑。修法：在 `run` / `preflight` 两个收口处加 `script_rel_path()`，只放行
「一个普通文件名」，8 个反例进单测。

## 三、第二轮：子 agent 解绑任务卡的漏项

`9ece807` 把子 agent 从「每派一个建一张任务卡」改成「只插一行 subagents」。
卡没了，原卡上的四件事各有新落点（契约上没问题），但**下游有四处没跟着改**。

### P1-3 取消后按「失败」上报，并沉淀一条空原因教训（`84de3d5`）

用户取消 → StopToken 打断 → `classify_outcome` 只给得出 `Failed`（文本里没有收尾
JSON）。原代码在「行已是终态（cancel 抢先）」时让收尾闭包返回 `None`，下游只能
用这个观感值。于是**每次用户取消**都会：审计记 `subagent_failed`、前端提示「子
任务失败」、并沉淀一条「执行任务「X」失败：。下次执行…」的空原因教训——与代码
注释「Cancelled 是用户选择不沉淀」正好相反。

修法：终态竞态时把行本身带回下游，`effective_status()` 以行为准（收尾闭包整体
失败才回落观感值）；事件名 / 审计 / lesson 闸门 / 事件 payload 全用它。加单测
锁住「cancel 抢先时不得报 Failed」。

### P1-4 排队期取消不发事件（`84de3d5`）

拿到槽位前的两条中止分支只写审计就 `return`，前端列表永远停在 `queued`。
修法：`emit_subagent_finished()` 统一出口，三处共用。

### P1-5 LLM 侧契约仍在讲已删的卡协议（`84de3d5`）

`SCHEMA_READ_OWN_CARD` 的描述与子 agent 系统提示（`SUBAGENT_BASE` 第 2–4 步）
还在让模型去找 `subtasks` / `note` / 「卡片被软删」——工具返回体里这些字段早没了，
而真正可靠的取消信号 `status=cancelled` 从来没在提示词里出现过。模型每轮照提示
找不到字段，也看不到取消信号。按行契约重写两处文案 + 镜像资产
`docs/prompts/subagent/subagent_base.md`。

### P1-6 子 agent 行永远不刷新（`464d398`）

`refreshSubagents` 全库只有切会话时那一处调用，`subagent-finished` 监听器只加提示。
解绑后子 agent 行**只有**聊天内嵌区与右侧栏两处可见，于是派发方会话里新派发的
看不到、跑完的还转圈。修法：事件到达即重拉（回调走 ref，拿得到当前 `sessionId`，
不会把旧会话的响应刷进来）。

### P1-7 用户侧没有任何取消入口（`464d398`）

旧的取消语义是「软删我的卡」，卡没了这条入口一起没了。剩下的两条路都够不着子
agent：停止键被 `viewedBusy`（`inflightSids`）门控，而子 agent 是后端跑的、
子会话又因 `WHERE is_subagent = 0` 不进会话列表。修法：内嵌区与侧栏的行内补停止
钮（`cancel_subagent`，key 传 `sa_` 行 id，后端 `resolve_row` 直查）。

### P2（第二轮）

- 六态被压成 running/error 两桶：`cancelled` / `budget_exceeded` 一律渲染成红色
  「失败」，把用户的取消说成系统出错；`STATUS_ICON.cancelled` 因此是不可达死
  分支。视图模型改为带真状态，两处 UI 按态分图标分词。
- `check_subagent_locked` 的 done 不封顶：子 agent 重复报同一条验收标准时会出现
  「3/2」这种自相矛盾的进度。
- `idx_subagents_task` 只在 `ensure_task_id_nullable` 的重建分支里建，新建库从
  来没有这个索引，而 `db/mod.rs` 的注释却称 DDL 含它。补进 `SUBAGENTS_DDL`。

## 四、第三轮：删除 / 级联 / 生命周期

### P1-8 删 A 卡的文件会连带毁掉 B 卡的引用（`e305d5a`）

`delete_bound_file` 的白名单是**全局**的（所有卡的绑定 + 工作区链接），同一条
路径可以同时被两张卡引用，且去重只在卡内做。回收站「全部删除」按卡循环调用，
于是删 A 卡会把 B 卡也绑着的文件移进回收站，B 的绑定变成死链，而 B 自己再删时
因幂等早返回静默无感；确认弹窗只列本卡文件，影响范围对用户是隐蔽的。

修法：命令加 `task_id`，命中全局白名单之后再判归属——路径仍被别的卡或工作区引
用就拒绝并指名持有者；前端三选项删除按卡传 id。读不到卡表时 fail-closed（判不出
独占不等于独占）。不传 `task_id` 保持旧口径。

### P1-9 调度扫描读库失败静默停摆（`e305d5a`）

`load_jobs_for_sched` 把 join 错误与 DB 错误一起吞成空表。整轮 for 不执行、无
日志、无审计，全仓唯一一处静默失败。更糟的是恢复后错过窗口的作业会被判「错过
消费」**吃掉且不执行**——一次瞬时 `SQLITE_BUSY` 就是一次永久丢失。修法：返回
`Result`，`jobs_tick` 记 `sched_jobs_scan_failed` 后返回。

### P2（第三轮）

- `delete_scheduled_job` 只删父行，`scheduled_job_runs` 成永久孤儿（无外键、无
  保留期清扫）。同事务级联。
- `trace_clear_before` 全表 DELETE 不持 `DB_WRITE_LOCK`，与并发写者抢 2s
  busy_timeout 后整条命令失败。补持锁。
- `bot_chat` 的 `bot_assigned` 写失败只有 `.is_ok()` 一句，失败连痕迹都不留
  （违反「不吞错误」）。补 `bot_assigned_commit_failed` 审计。
- REST 标完成与 Tauri `task_set_column` 不同口径：前者不清 `bot_assigned`，完成
  卡上继续挂着机器人头像。
- 删会话不清子 agent 终态行（`subagents` 无外键），成永久孤儿。级联清终态行，
  在途行不动（runner 还要靠它收尾）。
- 子 agent 僵尸行：进程重启后没有 runner 会再收尾 `running/queued` 行，不清就在
  面板里永远转圈。启动清扫一批：排队行按 `cancelled` 收、执行中的按 `failed`
  收——状态机只放行这两条边，且不越权改状态机。

## 五、第四步：对本轮修复的独立复核（`83cf8b2`）

修完不验证等于把问题换个地方存。第四步派了一路 verifier 只看这 7 笔提交的
diff，专查「修复本身有没有修错、修漏、引入新问题」，结果逮到 6 处**我自己刚
写的**缺陷，全部已修：

| 缺陷 | 为什么没被门禁抓到 |
|---|---|
| `sweep_zombie_subagents` 里 `lock_db_write()` 写成了独立语句——`DbWriteGuard` 非 `#[must_use]`，语句结束即释放，整段清扫实际无锁 | rustc 不警告未使用的 RAII 临时值；clippy 也不报 |
| 四条 runner 中止分支仍未发 `subagent-finished`（running 写失败 / gen_dir 失败 / 子会话创建失败 / 会话锁冲突），行会一直停在「排队中/执行中」 | 第一轮我只数了「排队期取消」那两条，兄弟分支没数 |
| 槽位复核读不到行时谎报 `cancelled`（DB 抖动被当成用户取消上报） | 只有读代码逐分支比对才看得见 |
| 工作区占用检查读库失败时 fail-open（与卡表侧口径相反） | 同上 |
| 彻底删除遇错即中断 → 只删掉一个任意前缀，其余文件与卡片状态对不上；且叠了两个弹窗 | 需要把「共享引用拒绝」这个新分支和既有循环放一起看 |
| 三处注释与实现对不上（helper 说明混进命令文档块、声称 budget_exceeded 有独立图标、把「启动清扫」说成运行期兜底） | 门禁不管注释 |

复核同时确认了这几处是对的：脚本路径闸不误伤合法调用（三处写入方都写死
`app.py`）；确认弹窗收敛后 `always` 三态往返完好、后端 60s 兜底未动、丢掉的会话
过滤只影响呈现不影响归属；`finalized = Some(current)` 仍在历史落库之后、任何写
副作用之前返回，「终态不二次改写」没被破坏；会话删除的级联只按本行两个键删，不
误伤别的会话；`trace_clear_before` 补锁不自死锁（`open_db` 不取写锁）；新增测试
逐个验证过「去掉修复就会红」。
