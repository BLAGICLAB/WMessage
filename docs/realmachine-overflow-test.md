## 为什么单测不够

单测只能证明纯函数在被喂进特定入参时表现正确。漏斗真正的风险集中在**跨模块的接缝**上，
这些地方单测结构性够不到：

| 接缝 | 坏了会怎样 | 单测能不能看见 |
|---|---|---|
| 指针路径 → `bot_fs::allowed_dirs` 白名单 | 模型拿到指针却读不回来，或更糟：静默弹授权框打断任务 | **不能**（白名单是 AppHandle 相关的真实目录） |
| 指针里的行数 → `read_text_file` 的 offset | 模型按错误行号翻页，拿到错段内容还以为是对的 | **不能** |
| cap 字节数 ↔ 指针里的字节数 | 两处口径不一致时，模型按指针估长度会误判"已读全" | **不能** |
| 模型是否**真的会去读**指针 | 机制全对，但模型不读 → 上下文里只剩节选，任务实质失败 | **不能** |
| 转存失败 → 四一截断兜底 | 磁盘满/权限拒绝时兜底路径从未在真机跑过 | **不能** |

所以真机测试的主体不是"再测一遍正确性"，而是**把这些接缝一个个撬开看**。

## 前提条件

1. **能跑起来的应用**：`npm run tauri dev` 或已打包版本。
2. **bot 已启用**：任务卡绑定目录 + `bot-enabled.flag` 存在（`exec_trace.rs` 里有 setup 先例）。
3. **开 Python 开关**：设置页「机器人设置」→ 打开「允许机器人执行 Python」，
   或把授权模式切成 yolo（yolo 免此开关）。否则 `run_python` 直接被拒，
   A/B/C/D/E/F 六个场景全部跑不了。注意这个开关**不在**「Agent 运行参数」卡片里。
4. **`工具结果截断字节数` 留空即可，不要动**。它的解析链是：

   | 界面填 | 前端发出 | 后端 `cfg.max_tool_output_bytes` | 实际 cap |
   |---|---|---|---|
   | 留空 | `null` | `None` | `DEFAULT_TOOL_OUTPUT_CAP_BYTES` = **30000 字节** |
   | 填 `0` | `null`（`n > 0` 判否） | `None` | **30000** |
   | 填 `30000` | `30000` | `Some(30000)` | `clamp(30000)` = **30000 字节** |

   三种写法结果一样，所以留空就行。

   ⚠️ **界面那行提示「默认不截断」曾与实现不符**——留空和填 0 都得到 30000 截断，
   不是「不截断」。后端认的 `Some(0) = 关闭截断` 界面根本发不出去（前端
   `n > 0 ? n : null` 把 0 吃掉了），所以「不截断」这个选项在界面上仍然不可达。
   提示文案已改成「留空 = 默认 30000 字节」，但「填 0 关闭截断」这条路依然不通。

   `run_python` 的 per-tool 预算是 8192，所以实际上限 =
   `min(8192, 30000)` = **8192 字节**——下面所有边界值都按 8192 算。
5. **终端 A** 常驻 `bash scripts/overflow-probe.sh watch`。

## 场景卡

### A. 边界三连（攻 `>` vs `>=`，对应存活变异 M5）

`run_python` 的输出是**裸 stdout、无包装**（`bot/tools.rs:1941-1956`），所以字节数完全可控。
`print(x, end="")` 精确产出 N 个字节（全 ASCII 时 N 字符 = N 字节）。

**跑法：先校准、再 A3 → A2 → A1**（提示词见上一节）。顺序不能反——
A1/A2 在界面上完全看不出来，必须靠日志分辨，而"日志可信"这个前提得由 A3 兑现
（`output_bytes=8193` 才说明模型真的照抄了代码）。

三段代码：

```python
# A3（先跑这个）：8193 字节，超出一个字节 → 必须溢出
print("A" * 8193, end="")
```

```python
# A2：8192 字节，正好等于 cap
print("A" * 8192, end="")
```

```python
# A1：8191 字节，恰好在 cap 内
print("A" * 8191, end="")
```

**预期**（现行实现取严格大于）：

| | `over_budget` | `spilled` | 模型看到 |
|---|---|---|---|
| A1 | 有 | **无** | 完整 8191 字节 |
| A2 | 有 | **无** | 完整 8192 字节 |
| A3 | 有 | **有** | 头尾节选 + 指针 |

> 建议顺手用 `grep_files` 在大目录上跑一遍真实场景：它的 cap 同样是 8192，
> 且是开发机历史上最高频的溢出源（见上文数据）。真实负载比构造负载更容易暴露问题。

**怎么判**：`report` 里数 `spilled` 出现次数，A1/A2 场景后应为 0，A3 后应为 1。
不要靠肉眼看聊天框判断"有没有指针"——A2 的结果和 A1 长得一模一样，正是要靠日志分辨。

**这个场景的价值**：M5（`>` 改成 `>=`）在单测里存活，A2 正是唯一能把它按死的输入。

### B. 单行撞上限（攻行数口径与嵌套溢出）

⚠️ **`run_python` 自己就有两层截断**，所以这个场景**产不出 200000 字符**：

| 层 | 位置 | 钳在 | 口径 |
|---|---|---|---|
| 字节层 | `py/runtime.rs:900/:915` `read_capped_drain(OUTPUT_CAP + 1024)` | 66560 | 字节 |
| 字符层 | `py/io.rs:101` `truncate_output` | 65536 + 9 字符截断标记 = **65545** | 字符 |

所以 `print("B" * 200000, end="")` 的真实结果是 **65545 字符**，不是 200000。

```python
print("B" * 200000, end="")
```

**预期**：

1. 转存成功，指针文案里出现 `1 行 / 65545 字节`——**行数是 1**（全程无换行）。
2. 节选是"头一半 + 指针 + 尾一半"。
3. **关键**：模型按指针 `read_text_file` 读回时拿到 65545 字符，而 `read_text_file`
   自己的 cap 是 **65536**——**又是 9 个字符之差**，触发**二次溢出**。

**怎么判**：`report` 里 `spilled` 出现 **2 次**，溢出目录有 **2 个**文件。

**这个场景暴露的真实行为（2026-10-19 实测修正）**：

初版分析以为「`run_python` 上限 65545 只比 `read_text_file` 的 cap 65536 高 9 个字符，
所以是个窄缝」。**实测证明这是错的**——`read_text_file` 的 per-tool 预算是 65536，
但 `effective_output_cap` 取 `min(65536, 全局 30000)` = **30000**。实测 spill 事件里
记的就是 `cap=30000`。

所以嵌套溢出的真实口径是：**溢出文件超过 30000 字符，读回时必然二次溢出**。
`run_python` 能产出最多 65545 字符，也就是说——

> **凡是 `run_python` 输出超过 30000 字符，模型读回指针文件时必定再溢一次。**

这不是边角，是 8192～65545 这整段区间的常态。好消息是这恰好**证明 L1/L2 取小在读回
路径上真的生效了**：per-tool 给到 65536 的工具，被全局 30000 兜住了。

### C. 4 字节 UTF-8（攻多字节内容上的字节口径）

```python
print("🎉" * 9000, end="")
```

9000 **字符** / 36000 **字节**。cap 是**字节**（36000 > 8192 → 溢出）。

**预期**：指针写 `36000 字节`，与 cap 同口径——两边数字对得上。节选总长按**字节**
≤ 8192，且切点落在 code point 边界上（不能切出半个 emoji，否则模型读到的是坏数据）。

**怎么判**：`overflow-probe.sh show <文件>` 打印的行数/字节/字符三个数应当自洽；
节选里扫一眼 emoji 是不是完整的。

**顺带记一笔既有行为**（不是本次改动引入的）：把 emoji 量加到撞上限
（`print("🎉" * 30000, end="")`，120000 字节），`py/io.rs:63` 的
`String::from_utf8_lossy` 是在 66560 **字节**处切的，切点可能落在多字节字符中间，
产出 `U+FFFD` 替换符。纯 4 字节 emoji 恰好整除（66560 / 4 = 16640）不会踩到，
但混合宽度内容会。观察到就记，别归到溢出漏斗头上。

### G. 白名单读回闭环（**最高优先级**，攻存活变异 M7）

这是整套方案里唯一一个**从未被任何自动化测试覆盖过**的接缝：
指针给出的路径，模型到底能不能直接读回来。

1. 先跑一次会溢出的场景（比如 A3），从 `report` 里抄下 `path=...` 那一行。
2. 新开一轮对话，把这个路径交给模型：

   > 用 read_text_file 读一下 `<粘指针路径>`，只读第 1 行，告诉我你读到了什么。

**预期**：

- **不弹授权框**。溢出目录恒在读白名单里（`bot_fs.rs:270`），白名单内直接读。
- 返回内容与转存文件一致。
- 若模型自己翻了页（offset/limit），说明指针的读法说明写得够清楚。

**怎么判**：屏幕上有没有弹出"请授权访问"的对话框。**弹了就是 FAIL**。

**这个场景的价值**：M7（把白名单里的溢出目录路径写坏）单测完全存活，
因为 `allowed_dirs` 在单测环境下解析不到真实目录。**这是唯一能抓住它的关卡。**

### H. 模型会不会真的去读（质量闭环）

上面的 G 是你把路径喂给模型的。这一条要看模型**自己**的行为。

> 跑一下 `print("F" * 9000, end="")`，然后告诉我最后一个字符是什么。

结尾特征已经写在节选尾部，所以这条测的是弱形式。想测强形式，把答案藏在**中间**：

> 跑一下 `print("H" * 8193, end="")`，把它的第 5000 到第 5010 个字符告诉我。

**预期**：模型应当先收到节选+指针，发现中间拿不到，再**主动**调 `read_text_file` 翻页取回。

**怎么判**：对话里出现 `read_text_file` 调用，且模型的回答与原文一致。
模型直接编一个答案 → FAIL（指针文案不足以让模型理解"还能再读"）。

**这个场景的价值**：机制全对但模型不用，等于功能没上线。这是唯一能暴露该问题的观察点。

### I. 保留期清扫（攻存活变异 M8 / M9）

```bash
bash scripts/overflow-probe.sh locate        # 记下 data_dir
ls "$DATA_DIR/overflow/"*/                   # 确认有文件
touch -t 202601010101 "$DATA_DIR"/overflow/*/*.txt   # 改成很久以前
# 完全退出应用，再启动（清扫在 setup 里跑一次）
```

**预期**：启动后那些文件消失，`overflow/` 下不再有对应日期目录。

**怎么判**：`find "$DATA_DIR/overflow" -type f` 为空，且 bot.log 里没有
`overflow.sweep_fail`。

**变体（正向）**：把另一个文件 `touch` 成**今天**，重启后它应当**还在**。
只测删除不测保留，M8（判定方向反过来）就抓不住——那个变异的表现是
"只删新文件、老的永远留着"，恰恰需要这个正向用例。

### J. 转存失败兜底（攻存活变异 M6）

```bash
chmod u-w "$DATA_DIR"/overflow/*/     # 把当天的日期目录设成只读
```

然后跑 A3。

**预期**：转存失败 → `tool.output.spill_failed` 记 Warn → **退回四一头尾截断**，
模型看到 `…（已按 maxToolOutputBytes=8192 截断…）…` 的说明。

**关键**：`report` 里出现的是 `spill_failed` 而**不是** `spilled`，且模型收到的**不是空串**。

**测完务必恢复**：`chmod u+w "$DATA_DIR"/overflow/*/`

**这个场景的价值**：M6（兜底返回 `String::new()`）单测存活。真机里如果兜底退化成空串，
模型会拿到一个空结果并当成"工具没输出"——这是最阴的失败模式，肉眼在聊天框里很难察觉，
只能靠日志里的 `spill_failed` + `show` 确认。

## 变异叠加：证明这套测试有牙齿

单测会变异，但真机场景也该证明自己能抓住问题。挑两个**单测抓不住**的变异，
注入后重跑对应场景，应当 FAIL。

```bash
bash scripts/mutation-trace-funnel.sh M7    # 单独跑一个变异确认注入成功
```

手动注入流程（脚本会还原文件，这里走手工以便中间插真机操作）：

```bash
# M7：把白名单里的溢出目录指向不存在的子目录
sed -e '270s|crate::overflow::root(app)|crate::overflow::root(app).join("nope")|' \
```

| 变异 | 重跑场景 | 应当 FAIL 于 |
|---|---|---|
| M7 白名单路径写坏 | **G** | 弹出授权框 |

### D 场景查出一个真实的数据损坏

```
原样执行：print("👨‍👩‍👧‍👦" * 3000, end="")
结果：original=18637 cap=8192，落盘 18637 字符 / 66560 字节
```

**末尾正好 1 个 `U+FFFD`**，位置在第 18636 字符（全文最后一个）。算术完全对得上：

| 项 | 值 |
|---|---|
| 一个家庭 emoji | 4 人 + 3 个 ZWJ = 7 codepoint / **25 字节** |
| `read_capped_drain` 字节钳 | 66560 字节（`OUTPUT_CAP + 1024`） |
| 装下 | 2662 个完整家庭 = 66550 字节 |
| 剩余 10 字节 | 👨(4) + ZWJ(3) + 👩 的**前 3 字节** |
| 结果 | 👩 被腰斩 → `String::from_utf8_lossy` 产出一个 U+FFFD |

2662 × 7 + 👨 + ZWJ + U+FFFD = **18637**，与审计日志分毫不差。

**为什么现在更要紧**：这个截断本身是既有行为（`py/io.rs:63`），但在溢出回灌落地**之前**，
U+FFFD 只活在一次性的工具结果里。落地**之后**，它被写进文件，而指针文案明确告诉模型
「已**完整**转存到本地文件」——**模型会把一个被截断的字符当作权威原文去分页读回**。

可选处置（都需要拍板，我没擅自改）：
- `read_capped_drain` 截断后回退到 UTF-8 字符边界，丢掉不足一字符的尾巴；
- 或 `truncate_output` 已有截断标记语义，让字节层也补一个标记，别让模型误以为是完整内容。

### H 场景为什么没测到

模型收到「第 5000 到第 5010 个字符是什么」后，**没有去读指针文件**，而是重新跑了一段
Python 自己算：

```
line1 length: 65536
first 20: b'BBBBBBBBBBBBBBBBBBBB'
chars 5000..5010: b'BBBBBBBBBB'
```

这不算功能失败——重算是合法策略，而且答案正确。但它**没测到我们想测的东西**。
重跑能成立是因为答案可从指令复现。要测「模型会不会去读指针」，问的内容必须**不可复算**。
重测时把提示词改成引用一个随机量，例如先让它写一个随机 UUID 再问该串第 3-5 位。

### 附带发现：幻觉守卫有一条误报

```
[21:40:46] hallucination_guard | 声称变更但未调工具: 已实际执行，未改动任何字符、未添加额外输出。
```

模型只是**复述了我的指令原文**（「未改动任何字符」），`改动` 命中了「声称变更」的启发式。
这是误报——模型确实没声称做过任何变更。测试类指令里带「改动/修改/删除」字样就会踩到。

另一个不是误报但值得记：21:39 那轮问 8191 时，模型**连着两次只口头声称执行、没真调工具**，
被守卫拦下，第三次才真的跑。这说明模型执行简单指令时并不可靠——
所以每个场景都必须以 `tool.return` 为准，不能以「模型说它跑了」为准。
