# D2 — 「注释逐条对照代码自查」机制复盘与硬约束草案（2026-09-21）

## 问题

C2b-1 起明文要求「新增/修改的注释逐条对照代码自查」。四批（C1b / C2a / C2b-1 / C2b-2 … C2d）
过去，**自查零命中**；而「注释/声明与实现不一致」被 OCR 抓出**四次**：
C1b 注释撒谎 → C2a Q1 设计-实现不一致 → C2b-1 H1 注释撒谎 → C2d-v7 over-claim。
（三次 OCR 抓、第四次仍是 OCR 抓。）

## 根因（一句）

**自查的输入是作者自己写的注释文本——「逐条对照」实际操作成了「重读注释」= 重读自己的意图，
而不是读代码；它既无独立信号（自证）、无可核产物、也无强制触发，因此在结构上不可能发现
「意图 vs 实现」的偏差。** 只有从**代码侧入口**读、再回头比对声明的**独立读者**（OCR）才可能发现
——所以「OCR 抓到、自查零命中」不是「不够仔细」，是该机制的设计必然。

（旁证：C2b-1 我确曾做了自查并"修正 1 处不实"——但那次修正靠的是**碰巧回读代码**，
不是机制；机制本身无强制回读代码这一步，所以四批里只偶然中过 0 次有效的 over-claim。）

## 硬约束草案（动作级，可执行、可核）

**核心动作：把「读注释」改成「读代码 + 写三元组」，且清单机械生成（不靠回忆）。**

1. **清单机械生成 + diff 基线写死**（A）：清单相对**该批的上一个 commit（或分支起点）**生成，
   并在 commit message 记录**基线 hash**；**不用 `git diff --cached`**（amend/rebase 后会漂，不可复现）。
   - 未提交批：baseline = 该批动手前的 HEAD；`git diff <baseline> -U0 | grep -nE '^\+\s*(///|//|/\*|\*)' | …`
   - 已提交批：`git diff <baseline>..<批末> -U0` 同法。
2. **每条一个三元组**（commit message 固定段落 `注释核对:`，必填）：
   ```
   <注释 文件:行号>  →  <证明/相关代码 文件:行号>  →  判定：一致  |  不一致(处理：改注释/改代码/删)
   ```
   判定**保持二元**（一致 / 不一致-处理）；不加「需验证」——遇到再加，不预先放宽。
3. **判定必须 code-first**：先打开第 2 步的「代码行号」**读代码**，再判一致性；
   **禁止**只重读注释下结论。读不到对应代码行 → 判定**不可能一致**。
4. **claim 必须可指认**：任何**断言行为的注释**（如「合并进一个 blocking 任务」）必须能指出
   **证明它的代码行号**；指不出 → 注释降级为中性表述或删除。
   （C2d-v7 正是此类：声称「合并进一个 blocking 任务」但 `db_load` 自带 `spawn_blocking`
   —— `src-tauri/src/db/tasks.rs:396-400`（`db_load_for` 内 `async_runtime::spawn_blocking`）。）
5. **显式豁免，且豁免可核**（B）：版权头 / 纯类型签名解释 / 纯描述性注释 → 不强制三元组，
   但**必须在清单里列出豁免行号 + 一句理由**。**沉默跳过 = 新的走过场口子**；显式豁免 = 可复核的克制。
6. **docs-only 批免格式、不免诚实度**（C）：docs-only 批**豁免三元组段落**；但 docs 内若**声称代码行为**
   （如「delete_bound_file 现在做二次 re-check」），**仍须指认代码行号**。文档免的是**格式**，不是**诚实度**。
7. **门槛语义**：`注释核对:` 段缺失、或有未判定条目、或有未声明的沉默跳过 = 该批**未完成**（不得收口/commit）。

**可核性**：任何人可拿该段的「注释行号」对着 diff 复核、对着「代码行号」读代码复判 —— 这是
旧自查缺的那条外部信号。
