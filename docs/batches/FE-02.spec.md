## 逐条处置（原文均已核）

**实修 ① ArtifactBatchDialog.tsx:34-43（high）**：listen/unlisten 竞态——`listen()` 返回 promise，cleanup `un.then((f) => f())` 不等待注册；组件卸载早于 resolve 时 listener 在 cleanup 后才挂上，永不注销（泄漏）；`.then` 无 `.catch` → unhandled rejection。
**修法**：cancelled flag 模式——`listen(...).then((u) => { if (cancelled) u(); else unlistenFn = u; }).catch(console.error)`；cleanup 置 cancelled + 同步调已就绪的 unlistenFn。 cancelled 后 resolve 的注册立即自注销。

**实修 ② ArtifactBatchDialog.tsx:35-39（high）**：confirm 在飞（busy=true）期间新 `artifact-batch-ready` 事件覆盖 ready/selected/error——A 批 confirm 成功后 `setReady(null)` 把用户正在看的 B 批弹窗杀掉；或 A 的错误显示在 B 上。
**修法**（finding 给的快照方向，非监听器阻塞方向——后者会延迟新批次提示）：confirm 入口快照 `const batch = ready`；成功后 `setReady((cur) => (cur === batch ? null : cur))`（期间到达的新批次保留）；失败仅当 `readyRef.current === batch` 才 setError（readyRef 经 useEffect 同步，不写渲染期）。顺带：confirm 加 busyRef 同步守卫（state busy 异步提交，同 tick 双击可双发 invoke——与 ④ 同族）。

**实修 ③ ConfirmMap.tsx:37-51（high）**：同 ① 的 listen 注册竞态（unmount 早于 resolve → 泄漏 + StrictMode 双注册）。
**修法**：同 ① cancelled flag 模式 + `.catch(console.error)`。

**实修 ④ ConfirmMap.tsx:65-82（high）**：respond() 重入不安全——`if (!cur || busy) return` 读 state，`setBusy(true)` 下一渲染才提交；倒计时归零的 `respond(false)` 与按钮点击可同窗双发 `bot_confirm_response`（同 id 重复/矛盾响应）。
**修法**：busyRef = useRef(false) 同步镜像——`if (!cur || busyRef.current) return; busyRef.current = true;`（check-and-set 同步），finally 复位。state busy 保留仅驱动按钮 disabled。

**转 B 类 ⑤ ArtifactBatchDialog.tsx:79（skip 语义方向）**：finding 称 skip 不通知后端会「卡 pending / 阻塞后续」。**核后事实**：后端无 ack 协议——`should_emit` 用 peek 不取（bot_artifacts.rs:82），`confirm_artifact_batch` 空 paths 早返不清登记（:110），emit 是 fire-and-forget（bot_chat.rs:1474 `let _ =`）；skip 后登记表保留，下次执行同任务重弹。「阻塞后续处理」无证据。真实缺口 = 无「永久 dismiss」路径（垃圾产物每次执行都重问）。修法方向涉语义+新命令：A=维持现状+注释文档化（skip=这次不绑下次再问）；B=新增 dismiss 命令清登记（扩 scope：新 Tauri command）；C=skip 走 confirm 空 paths + 改后端早返为清登记（后端行为变更）。**B 类攒批第 20 项**。

**转 B 类 ⑥ ConfirmMap.tsx:40-45（pending 覆盖方向）**：新 bot-confirm 到达直接覆盖未响应的 pending，旧 id 靠后端 60s 兜底超时拒绝。**核后事实**：后端每个 confirm 独立 uuid + oneshot + 60s 超时（bot_slash.rs:297-341），并发未决合法；前端单窗 UI 是瓶颈。修法方向：A=前端队列（逐个展示，UX 延迟但无静默拒绝）；B=切换前自动拒绝旧 id（加速必然结果，但用户未看到的请求被立即拒）；C=维持现状靠 60s 兜底（文档化）。语义方向 = **B 类攒批第 21 项**。
